# RFC-006: In-house SHA-512 (FIPS 180-4) — the zero-dependency close-out

- **Status:** DRAFT (stage 1 — slicing done; architect rounds 1 and 2
  both run and applied 2026-08-15 — round 1: 4 lenses, ~24 deduped fixes;
  round 2: 4 lenses, ~20 deduped fixes; no open forks either round; both
  mandatory rfc-flow rounds complete — ready for stage 3, `/tdd`). Drafted 2026-08-14 out of
  the validation-infrastructure design
  session (the grill that is producing RFC-005): the question "how much do we
  really rely on nimcrypto?" surfaced the asterisk this RFC removes.
- **Numbering / ordering:** RFC-005 is reserved for the test-suite/CI RFC
  still being designed. This RFC is independent of it and deliberately small;
  it may be implemented before or after 005. If 005 lands first, this work
  gets CI coverage from birth; if this lands first, 005's CI arrives to a
  zero-dependency tree. Ordering is Corey's scheduling call at stage 3, not a
  design constraint.
- **Handoff doc:** `docs/rfc-006-sha512.handoff.md` (created when stage 3
  opens).
- **Standing orders:** identical to RFC-001..004 (PhD-CS bar; no consumers
  yet, breaking changes sanctioned; genuine forks escalate; wrong-spec
  assumptions escalate; per-slice commits after gates pass).
- **Spec:** FIPS 180-4 (SHA-512 only — not 224/256/384, not the /t truncated
  variants), plus NIST SHAVS for the Monte Carlo test methodology (round 1:
  the chain structure slice 2 transcribes comes from SHAVS, not FIPS 180-4 —
  a vector-methodology spec the draft never cited). Where this RFC
  paraphrases the algorithm, the SPEC is
  authoritative and the implementing slice must transcribe from it, with the
  NIST CAVP vector corpus as the zero-tolerance gate — the same register
  RFC 8032/7748/9496 hold for the existing layers. This RFC AMENDS the brief:
  `prompt.md` deliberately made SHA-512 the one primitive sello does not
  reimplement; Corey approved reopening that scope cut 2026-08-14.

## Context

sello's production dependency on nimcrypto is exactly two import sites
(`challenge.nim`, `private/backend.nim`), four `sha512` context
instantiations (`challenge` ×1, `derivePublic` ×1, `signDetached` ×2 —
grep-verified in round 1; the draft said five), serving ed25519 only —
X25519 needs no hash and `ristretto.nim` is nimcrypto-free by design
(callers hash). Two test files import nimcrypto besides:
`tests/unit/test_scalar.nim` (SHA-512 as a deterministic PRNG and seed
expander inside its own oracles, three instantiations) and
`tests/unit/test_ct.nim` (context-wipe coverage naming the nimcrypto type);
both are on slice 3's swap list — the draft's swap list missed
`test_scalar.nim` entirely, which would have broken compilation at the dep
drop. Correctness of that dependency is already pinned
transitively: every RFC 8032 KAT is an end-to-end vector through SHA-512, so
a single wrong bit in the compression function fails the whole signing suite.
Supply chain is pinned by commit SHA + content hash in `milpa.lock`.

What is NOT covered is the asterisk this RFC removes: **the seed — the root
secret — flows through third-party code held to none of sello's hygiene
discipline.** `backend.derivePublic`/`signDetached` feed the seed into
nimcrypto's `update`/`finish`, whose internals were never audited to sello's
stack-only/wipe bar (sello wipes the *context object* afterward — verified
flat, no hidden heap — but has no say over the message schedule and working
variables nimcrypto's own compression call leaves on its stack frame). Timing
is covered only empirically (dudect measures `signDetached` end-to-end), not
by construction. That is the same class of asterisk the libsodium backend
exists to *acknowledge* — except this one sits in the default pure-Nim path.

In-housing SHA-512 is the cheapest primitive validation sello will ever do:
~150 lines of pure ARX (add/rotate/xor — no tables, no secret-dependent
branch or index anywhere in the algorithm, constant-time by nature), the
richest KAT corpus in existence (NIST CAVP short/long/Monte Carlo), a
differential oracle already wired into the harness (libsodium's
`crypto_hash_sha512` under the existing `-d:selloLibsodium` machinery), and a
validation bar that applies almost mechanically. The payoff is the completed
trust story: **zero dependencies, every line held to the same bar**, and no
third-party code touching a seed.

## Design

### Module: `src/sello/private/sha512.nim`

A new leaf module, `private/ct.nim`'s sibling in the layering: imports
nothing but `sello/private/ct` for its own wipes — unconditionally, not
"optionally" (round 2: the wipes are mandatory per Hygiene below, and the
import description must not read as if a wipe-free build were licensed);
consumed by
`challenge.nim` and `private/backend.nim`. Under `private/` because it is
NOT public API — see Non-goals: sello is a 25519 library, not a hash
toolkit, and the module is deliberately absent from the facade (the
`scalar.scMulAdd` non-export precedent).

- **Types/API — fixed-arity one-shots as the production face (round-1
  design finding, superseding the draft's "mirror nimcrypto's shape so the
  swap is mechanical"):** every production call site hashes a fixed, known
  set of 1–3 buffers and immediately finishes — none streams
  (`derivePublic`/`signDetached`'s seed hash: one part; `signDetached`'s
  nonce hash: two; `challenge`: three; verified against the code). The
  module's face is therefore three fixed-arity one-shot funcs —
  `sha512(a)`, `sha512(a, b)`, `sha512(a, b, c)` over `openArray[byte]`,
  returning `array[64, byte]` by value — each internally running
  `init`/`update`×N/`finish` and `ct.wipe`-ing its own context before
  returning (the module's `raises: []` push means no exception path can
  skip that wipe). Call sites collapse to a single expression; the
  caller-side `var sha`/`var nonceSha` declarations and every caller-side
  `ct.wipe(sha)` (happy-path and `finally`) are DELETED, not migrated —
  context lifecycle and hygiene live in one audited place, and
  reuse-after-finish misuse is structurally impossible for production
  callers because no context is caller-visible at all. The whole face is
  `func` (round 2, stated rather than left to guess in a codebase that
  treats the choice as load-bearing): matching `challenge.nim` and
  `ct.wipe`'s own func-compatibility, and the reason `backend.nim`'s
  exports are `proc` — dispatch-parity with the FFI-backed sodium
  adapter (round-3 finding A4) — has no analog here, since no backend
  ever dispatches to a second SHA-512. The arity ceiling is also
  recorded (round 2): Nim cannot express `varargs[openArray[byte]]`
  (openArray does not nest), which is precisely what makes the
  fixed-arity family the deep design rather than a compromise; no 4-part
  caller exists, and a future one escalates rather than growing the
  family or hand-concatenating parts into a caller-side scratch buffer
  (which would reopen the residue question the one-shots exist to
  close). A streaming
  register — `Sha512Context` (fields private) + `init(var Sha512Context)`,
  `update(var Sha512Context, openArray[byte])`, `finish(var Sha512Context,
  var array[64, byte])` — stays exported for the test estate only, and
  round 2 narrowed the consumer list the round-1 text overstated: CAVP
  LongMsg is a single buffer and the Monte Carlo chain step is literally
  `sha512(a, b, c)`, so BOTH route through the one-shots (the heaviest
  corpora thereby validate the exact functions production calls, a
  strictly stronger signal than exercising a parallel test-only path);
  the genuine streaming consumers are only the incremental/split-point
  suites (which place `update` boundaries deliberately) and
  `test_ct.nim`'s whole-object wipe-scan (which needs a live context to
  inspect). Contract stated rather than implied, extended by round 2
  beyond finish-terminality: `init` unconditionally resets every field
  (state to the IV, fill and length counters to zero) and is supported
  on a fresh, mid-stream, or finished context — the reuse path a
  vector-loop consumer needs ruled IN; `update`/`finish` on a
  never-`init`ed context is undefined, and the failure mode is a
  plausible-looking wrong digest, not a crash (a
  `default(Sha512Context)`'s zero state is not the IV); `finish` is
  terminal — a further `update`/`finish` without an intervening `init`
  is caller error, deliberately not type-gated (recorded decline of a
  move-only/sink `finish`: the register's only consumers are test suites
  hashing public vectors; production goes through the one-shots). Naming:
  `Sha512Context` is kept over a `field.Fe`-style short `Context` — under
  Nim's unqualified default import a bare `Context` is collision-prone,
  and post-one-shot the type appears only in test code, where
  self-flagging beats brevity. No `=destroy`/`secretHooks` on the context
  — recorded decline: production contexts are module-confined and
  deterministically wiped before every return, and the streaming register
  hashes only public test data; a destructor would duplicate the first
  and serve nothing in the second.
- **Context layout:** flat, fixed-size only — `array[8, uint64]` state,
  `array[128, byte]` block buffer, buffer fill counter, and a 128-bit
  message length as two `uint64`s (spec-faithful: FIPS 180-4 pads with a
  128-bit bit-length; a single uint64 byte counter cannot represent it even
  though it is unreachable in practice — take the spec's shape, it costs one
  word). The type must remain free of `seq`/`ref`/`string` so the generic
  `ct.wipe` covers the whole state — the same property `ct.nim` documents
  (and `test_ct.nim` pins) for nimcrypto's context today; that verification
  moves to the new type. Three round-1 additions: (a) block→word decode
  (bytes into `W[0..15]`), state→digest encode, and — round 2, the same
  uint64→big-endian risk class, previously unnamed alongside the other
  two — the 128-bit length-field write into the final padded block are
  explicit per-byte shift/or assembly in FIPS 180-4's big-endian
  convention — the
  `feFromBytes`/`feToBytes` register, never a pointer cast or `copyMem`
  onto the `uint64` arrays: every validation instrument in this repo runs
  on a little-endian host, so an endianness-dependent shortcut would pass
  the entire estate while being wrong on a big-endian target (the exact
  currently-unguarded gap RFC-005 names for the existing code). (b)
  Padding is constructed in place in the context's own persistent block
  buffer — when finalization needs a second block (fill ≥ 112), it reuses
  that same buffer field, never a fresh stack scratch array — so the
  context wipe remains a complete residue guarantee with no separate
  finalization scratch to miss. (c) The 128-bit length's high-word carry
  (low-word overflow at 2^61 input bytes) is unreachable by any physical
  input and is verified by code inspection against FIPS 180-4 §5.1.2
  only, not by a running test — a recorded decline, same register as the
  K/IV constants below.
- **Hygiene — the point of the RFC:** the compression core wipes its own
  message schedule W (`array[80, uint64]` — secret-derived whenever the
  input is seed material) and its eight working variables before returning,
  via `private/ct.wipe`. This is precisely the discipline nimcrypto never
  promised. Uniform behavior on every call — the verify path hashes public
  data and needs none of this, but a skip-wipe fast register would be a
  second, type-untracked code path with no compiler signal separating it
  from the hygiene-bearing one: unlike `scalarmultVartime`, no
  `SecretScalar`-style type gate is available here, because a hash context
  has no type-level notion of "this input is secret." (Round 1 corrected
  the draft's `challenge.nim` drift-disease analogy on this point — wiping
  cannot change output, so output drift was never the risk; an unflaggable
  hygiene fork is.) Wiping is harmless on public data and the cost is
  bounded (a ~700-byte volatile store per 128-byte block, against 80 ARX
  rounds of real work — measured in slice 1 via a throwaway
  `-d:selloSha512NoWipe`-gated comparison: compile twice under
  `-d:release`, `std/times` wall-clock over ≥1e5 iterations, ratio
  recorded in the slice's commit message, no new permanent script;
  expected single-digit percent — if measurement says otherwise, that is a
  recorded finding to escalate, not a license to silently fork the path).
  The wipe's *survival* is additionally disassembly-verified in slice 4: W
  and the working variables are dead locals, exactly the shape the
  optimizer is entitled to dead-store-eliminate and the elision RFC-001
  slice 8 caught in the x25519 ladder. Production callers hold no context
  to wipe (see Types/API — the one-shots wipe internally); digest-OUTPUT
  hygiene (`ct.wipe(h)`, `ct.wipe(nonceHash)`) stays caller-owned,
  unchanged. One recorded assumption rides on that caller-owned wipe
  (round 2): the one-shots return `array[64, byte]` by value, and the
  claim that the caller's wiped array is the ONLY digest copy assumes
  Nim's large-array return codegen constructs the result in caller
  storage (a hidden out-pointer) rather than materializing a temporary
  in the one-shot's own dead stack frame — exactly the class of codegen
  assumption this repo verifies rather than trusts (the sink/move and
  assert-stripping empirical findings). Slice 4's disassembly check
  therefore covers the two secret-bearing call sites' return paths
  (`h = sha512(seed)`, `nonceHash = sha512(prefix, msg)`) in addition to
  the core wipe; if a temporary copy IS found, the recorded fallback is
  an `Into`-style out-param overload (`sha512Into(dest: var array[64,
  byte], ...)` — the streaming `finish`'s own out-param convention) for
  the secret-bearing sites, applied as a recorded finding, not a silent
  design change.
- **CT posture:** constant-time by construction and by nature, stated
  precisely (round 1 narrowed the draft's "no data-dependent branch, index,
  or table anywhere"): no branch, index, or table depends on message
  *content*; block and round counts are a function of message *length*
  only, and every current call site's length is public or fixed (a 32-byte
  seed) — a future caller with a secret-*length* input would need a fresh
  CT review of the padding path specifically. The implementation must
  preserve content-independence (straight-line rounds, `Ch`/`Maj` as the
  standard bitwise forms, no lookup tables). `{.push checks: off.}`
  on the compression core per convention; module carries the standard
  `{.push raises: [], gcsafe.}`.
- **Source & attribution:** implemented from FIPS 180-4 directly (the spec
  is short and complete), attributed in the module header per the standing
  ritual. `NOTICE` gains FIPS 180-4 / NIST CAVP entries; nimcrypto's entry
  is retired with a one-line historical note (it served through 0.4.0).
  The K round constants and IV are transcribed from the spec's own hex;
  their number-theoretic derivation (fractional parts of cube/square roots
  of the first primes) gets NO in-repo re-derivation test — the CAVP corpus
  is the right instrument for a wrong constant (any single-bit error fails
  it immediately), the same recorded-decline register as feSqrtRatioM1's
  A.4-vectors-not-symex decision.

### Dependency removal

`milpa.kdl` drops the nimcrypto dep; `milpa fetch` regenerates `nim.cfg` and
`milpa.lock` without it. `sello.nimble` drops its
`requires "nimcrypto >= 0.7.3"` line entirely (round 1: the draft missed it
— left in place, `nimble install` keeps fetching a dependency the library no
longer uses, making the zero-dependency claim false on that consumption
path; NOTICE's text pointing at that line goes with it), and its header
comment stops naming nimcrypto. sello's resolved-dependency count becomes
zero on both consumption paths (proptest remains, optional and dev-only — a
downstream consumer's plain `milpa fetch` resolves nothing at all).
`scripts/*` need no *behavioral* changes, but the draft's "they never name
nimcrypto" was false in prose: `scripts/test.sh` (header lines naming
`_deps/nimcrypto`, and the "`_deps/` contains only nimcrypto" comment),
`scripts/mutation.sh` (nimcache-reuse comment citing nimcrypto as its
example dependency), and `tests/mutation/run_mutation.py` (round 2: its
own header comment cites nimcrypto as the same nimcache example, one file
lower in the same call chain) get their comments corrected to the post-removal state
(`_deps/` empty on a plain fetch, populated only by `--features proptest`).
CLAUDE.md's "SHA-512 is the one dependency we do not reimplement" story
inverts, README's dependency pitch updates, and the `ct.nim` module doc's
nimcrypto references move to the new module.

### What must NOT change

`challenge(R, A, msg)`'s output for every input (sign/verify agreement),
`derivePublic`/`signDetached`'s outputs for every seed — i.e. the entire
RFC 8032 + Wycheproof + property + interop estate stays green with ZERO
vector change. The transitive pin that today protects nimcrypto's
correctness becomes the acceptance gate for its replacement. The public
facade is byte-for-byte untouched.

## Slices (each one `/tdd`-sized)

1. **Core + CAVP KATs** — two internal `/tdd` sub-slices (round 2: the
   parser and the core have independent RED cycles, and one
   undifferentiated bucket was over-bundled against the repo's own
   RFC-004 8a/8b/8c/8d slicing convention). Prerequisite, flagged
   honestly (round 1): the CAVP `.rsp` files (SHA512ShortMsg.rsp,
   SHA512LongMsg.rsp, SHA512Monte.rsp) must be downloaded from NIST by
   hand and placed under `tests/vectors/` before 1a's first real-corpus
   test — the container has no network, ever, so vector arrival is a
   host-side human step, not part of any script.
   **(1a) Vectors + parser.** The CAVP corpus vendored VERBATIM as `.rsp`
   (strongest provenance — the Wycheproof vendor-verbatim register)
   parsed by a new `tests/unit/cavp_vectors.nim` loader
   (`wycheproof_vectors.nim`'s sibling — named as real, sized slice work:
   no `.rsp` parser exists in this repo, every prior corpus is JSON).
   Round 2 named its actual shape: the corpus is TWO record formats, not
   one — `Len`/`Msg`/`MD` triples (ShortMsg/LongMsg) vs.
   `SHA512Monte.rsp`'s single `Seed` plus 100 `COUNT`/`MD` checkpoints
   (no `Msg` field at all; Monte inputs are chain-derived, never read
   from the file) — so the module is two typed loaders sharing low-level
   helpers, exactly `wycheproof_vectors.nim`'s own
   `loadEd25519Vectors`/`loadX25519Vectors` precedent. Its first RED runs
   against a tiny hand-written `.rsp`-shaped fixture, independent of
   `sha512.nim` existing at all. Also here (round 2): the
   padding-boundary lengths get a named source of truth — 129, 239, and
   240 bytes ALL fall outside ShortMsg's 0–128-byte range, and LongMsg is
   a sparse curated set that cannot be assumed to contain them — a
   checked-in host-side generator
   `tests/vectors/gen_sha512_boundary_vectors.py` (Python
   `hashlib.sha512` as the independent second implementation; the
   `gen_scmuladd_vectors.py` checked-in-generator-plus-provenance
   register, NOTICE entry included) produces their expected digests.
   **(1b) Core.** `private/sha512.nim` (one-shot funcs + streaming
   register per Design, compression core with wipe discipline); CAVP
   ShortMsg AND LongMsg KATs driven through the ONE-SHOT face (round 2:
   LongMsg is a single buffer — no streaming needed, and routing it
   through the one-shots means the heaviest KAT corpus validates the
   exact functions production calls); `tests/unit/test_sha512.nim`
   registered in `scripts/lib/unit-test-files.sh`; deterministic
   padding-boundary cases (0, 1, 111, 112, 127, 128, 129, 239, 240 bytes
   — both sides of both pad thresholds and a two-block message) in BOTH
   registers: one-shot lengths AND explicit incremental splits placing an
   `update` boundary exactly at each threshold — random split-point
   sampling (slice 2) is not guaranteed to land on the exact boundary
   bytes where a buffer-fill bug would hide. The wipe-cost measurement
   (see Hygiene) runs here as measure-record-REVERT (round 2 — its
   lifecycle was unstated and in tension with Hygiene's own anti-fork
   principle): the throwaway driver lives in uncommitted scratch (never
   `tests/` or `src/`, per the standing scratch-file convention), and the
   `-d:selloSha512NoWipe` branch itself is DELETED from
   `private/sha512.nim` in the same slice commit once the ratio is
   recorded — a compile flag that silently disables secret wiping must
   not survive as a standing, untested second register.
2. **Monte Carlo + properties + differential oracle.** CAVP Monte Carlo
   per SHAVS, transcribed rather than reconstructed (round 1): seed the
   chain MD₀ = MD₁ = MD₂ = Seed; each of 100 outer checkpoints runs 1000
   inner iterations of MDᵢ = SHA-512(MDᵢ₋₃ ‖ MDᵢ₋₂ ‖ MDᵢ₋₁); the
   checkpoint digest is compared against the `.rsp` and reseeds the next
   outer round. The inner step is implemented as the production
   three-part one-shot, `sha512(md3, md2, md1)` — round 2: the chain
   formula IS `sha512(a, b, c)`'s exact signature, so the heaviest
   chained corpus exercises the production face 100,000 times with no
   streaming context involved. All 100 checkpoints run by default, with
   a budget and a named fallback (round 2 — `scripts/test.sh` compiles
   unit files without `-d:release`, so ~200,000 debug-build compressions
   land in the everyday edit-test loop, a cost the round-1 text left
   with no contingency): measured debug runtime is recorded in the slice
   commit, and if it exceeds the current slowest standing unit file, the
   default run keeps a deterministic checkpoint prefix (e.g. the first
   10 of 100 — still genuine `.rsp` comparisons, not synthetic) with the
   full 100 behind an explicit define (`-d:selloSha512MonteFull`), the
   split recorded in the slice commit rather than discovered after
   landing. proptest properties in
   `tests/unit/test_properties_sha512.nim`, registered in
   `scripts/lib/unit-test-files.sh` (the existing `test_properties_*.nim`
   glob handles its proptest-absence skip): incremental-vs-one-shot
   agreement over random split points, determinism, multi-`update`
   associativity. MOVED HERE from slice 4 (round 1 resequencing): the
   libsodium differential sweep — a `sodiumHashSha512` wrapper added to
   `private/backend_sodium.nim` (the ristretto oracle wrappers' register,
   named as new work), then `crypto_hash_sha512` vs. the new module,
   one-shot + random-split incremental, in `test_libsodium_interop.nim` —
   so the implementation is differentially validated against an audited
   SHA-512 BEFORE slice 3 lets it sign anything (RFC-004 slice 8c's
   precedent: the oracle lands with or before first production use).
3. **Consumer swap + dep removal.** Internal order is load-bearing
   (round 1) — swap everything, gate, THEN drop, gate again: (a)
   `challenge.nim`, (b) `private/backend.nim` — production call sites
   collapse onto the one-shots, their `var sha`/`var nonceSha`
   declarations and every caller-side context wipe deleted per Design,
   doc-comment references to `Sha2Context` updated in the same pass —
   then (c) `tests/unit/test_scalar.nim` (the swap consumer the draft
   missed) — its three sites are single-buffer hashes and become plain
   `sha512(x)` one-shot calls, not a mechanically renamed streaming idiom
   (round 2) — and (d) `tests/unit/test_ct.nim`, all while nimcrypto is
   STILL resolvable; (d′) re-anchor the three mutation-catalog entries
   whose exact-string OLD text this swap deletes (round 2, grep-verified:
   `C01`/`C02` target `challenge.nim`'s `sha.update(R)/(A)/(msg)`
   triplet, `B03` targets `backend.nim`'s `nonceSha` block — all three
   collapse into one-shot calls, and `run_mutation.py` hard-fails the
   ENTIRE run on a zero-occurrence OLD, so `scripts/mutation.sh` would
   crash, not degrade; `B01`/`B02`/`B04` were checked and survive, their
   OLD text being post-hash byte assembly that the swap leaves
   untouched) — each rewritten against its new one-shot call site
   preserving the defect class (`C01` → argument-order swap in
   `sha512(R, A, msg)`, `C02` → a dropped `A` argument, `B03` →
   `sha512(msg, prefix)` order swap), the `F23` re-anchoring precedent
   in `docs/mutation-results.md`; (e) FIRST GATE: full suite green under both
   `scripts/test.sh` and `scripts/test-libsodium.sh`; (f) only then
   `milpa.kdl` drops nimcrypto (`milpa fetch` regenerates
   `nim.cfg`/`milpa.lock`) and `sello.nimble` drops its `requires` line;
   (g) SECOND GATE: both scripts green again, zero vector change across
   both. `test_ct.nim`'s context-wipe coverage moves to `Sha512Context`
   as a whole-object byte-scan (`cast[ptr UncheckedArray[byte]]` over
   `sizeof(Sha512Context)`, every byte checked zero — strictly stronger
   than the old field-by-field check, catches struct padding, and is the
   only shape compatible with fields-private, which a foreign-module
   field-by-field check is not).
4. **Adversarial depth.** Mutation batch (~10 mutants — round 2 added
   the two most classic hand-ported-compression bug classes the round-1
   list missed: a `Ch`/`Maj` boolean-formula error and a per-round
   working-variable rotation misorder (the `h←g←f←e←d←c←b←a`
   reassignment chain), joining the K-constant tweak, Σ/σ
   rotation-amount off-by-ones, σ-function swap, IV word tweak, padding
   length-encoding error, message-schedule index error, and buffer-fill
   boundary flip — each verified red against the full unit suite,
   `run_mutation.py`'s real methodology: CAVP KATs PLUS slice 1's
   deterministic padding-boundary cases, since CAVP vector lengths alone
   are not guaranteed to hit the exact 111/112/239/240 edges the
   buffer-fill mutant needs; catalog 73 → ~83, `scripts/mutation.sh`'s
   measured wall clock re-recorded post-addition per its own header's
   convention); one dudect target, concretely specified (round 1): fixed
   512-byte (4-block) message class vs. fresh random 512-byte draw per
   sample, single one-shot call, digest folded via `opSignDetached`'s
   existing 64-byte shl/or accumulation idiom (round 2: the harness's
   `foldBytes32` is hard-typed to 32 bytes and cannot take a SHA-512
   digest — the harness carries two fold idioms, and the RFC now names
   which one applies) — 4 blocks buys real margin over the
   sub-1000-cycle resolution floor that bit `` ristretto.`==` `` (whose
   carve-out precedent applies if the instrument bites anyway). ONE
   target, with the shape-equivalence argument stated rather than
   implicit (round 2): production's other call shapes (the 32-byte
   single-block seed hash, `sha512(prefix, msg)`'s two-part split)
   differ from the measured shape only in length structure and `update`
   boundaries, both PUBLIC under the module's content-independence
   posture — timing can vary only with content if that posture is
   violated, and content-dependence is shape-invariant, so one
   content-vs-content target at maximal block count (best margin over
   the resolution floor) measures the property for every shape; a
   per-shape second target would re-measure the same property closer to
   the floor. Disassembly verification (round 1; the RFC-001 slice 8
   x25519-ladder register): `-d:release` driver build, objdump, confirm

## Ordering & risks

- Slices are strictly sequential; 3 is the risk concentrator (the swap) and
  is gated by the zero-vector-change rule, which makes regression detection
  automatic rather than judgment-based — and, post-round-1, the swap is
  additionally preceded by the slice-2 libsodium differential sweep and
  internally ordered swap-first/drop-second with two separate green gates,
  so no intermediate commit can be red under either test script. Round 2
  adds the mutant re-anchoring step (3(d′)) inside the same slice, so
  `scripts/mutation.sh` also stays runnable at every commit rather than
  crashing on orphaned exact-string patches.
- The wipe-cost measurement in slice 1 is the one place reality could push
  back on the design (see Hygiene above); the escalation path is recorded
  there.
- CAVP vendoring: NIST distributes response files (`.rsp`); slice 1 vendors
  them verbatim with provenance noted in NOTICE (the Wycheproof register)
  and builds the repo's first `.rsp` loader. The files themselves arrive by
  a manual host-side download — no network at test time or fetch time, per
  the standing container constraints.
- RFC-005 (independent, in-flight) names this module's compression core as
  a future CT-taint (§A1) and disassembly-gate (§A2) target once that
  infrastructure lands; nothing here blocks on it, and nothing is owed
  beyond keeping the compression core an independently callable unit
  (already true), so a later RFC-005 slice can target it without
  refactoring `private/sha512.nim`. Slice 4's one-off objdump check is the
  interim, hand-run form of what RFC-005 §A2 would automate.

## Non-goals (considered and declined)

- **Facade export of SHA-512.** sello is not a hash toolkit; exporting
  would create a support surface (streaming API stability, HMAC requests,
  variant requests) orthogonal to the library's mandate, and ristretto's
  callers-hash design stays as is. A consumer who needs a general-purpose
  hash should use a hash library; the `scMulAdd` deliberate-non-export
  precedent applies. The expansion question ("export this, or grow other
  SHA variants?") was raised and grilled at stage 1 (2026-08-15) and is
  CLOSED, not deferred: the necessity defense that justifies this whole
  RFC — the seed flows through SHA-512, so SHA-512 must meet the hygiene
  bar — covers exactly one primitive; no secret in sello ever touches
  SHA-256/384, so their validation estates (CAVP corpora, mutation
  batches, dudect targets, differential sweeps) would buy zero 25519
  assurance while converting the pitch from "the minimal audited 25519
  surface" into "a growing crypto toolkit." **The revisit path is
  extraction, not export:** if a validated pure-Nim hash surface is ever
  wanted (janus's SHA-256/HMAC-SHA2 needs are the realistic demand
  signal — note janus needs a hash sello does not even implement), the
  move is extracting `private/sha512.nim` into a sibling library whose
  mandate IS hashing; sello's facade never grows a hash. That sibling
  library is recorded here only as the shape future work would take if
  it ever happens — it is explicitly not planned, committed, or implied
  work (the stack-wide zero-dependency ambition it belongs to was
  weighed in the same grill and declined as open-ended scope).
- **SHA-224/256/384, the /t variants, HMAC, HKDF.** ed25519 needs exactly
  SHA-512; everything else is toolkit scope. (SHA-384's "just a different
  IV plus truncation" cheapness is the completeness trap named in the
  stage-1 grill: nearly free to implement, never free to ship — it is a
  facade question, a CAVP vendoring, and a mutation batch for a variant
  with zero consumers. The extraction-not-export resolution above governs;
  an implementing slice that feels this pull escalates rather than adds.)
- **Replacing `ristretto.nim`'s caller-hashes design.** RFC 9496 §4.3.4
  leaves the hash out of scope and RFC-004 recorded that boundary
  deliberately; nothing here reopens it.
- **A `-d:selloNimcrypto` compatibility flag.** One implementation, no
  dispatch — the whole point is removing the second code path, and the
  libsodium adapter already serves the "audited implementation" want.
- **Vendoring nimcrypto's sha2 source instead of reimplementing.** (Round
  1, recorded for completeness.) Vendoring changes provenance, not the
  property at issue: the seed would still transit code held to none of
  sello's hygiene discipline — no schedule/working-variable wipes, not
  written to this repo's CT/stack-only conventions — unless rewritten
  anyway, and the rewrite IS this RFC. ~150 lines from a short, complete
  spec with the richest KAT corpus in existence is the rare case where
  reimplementation is cheaper than adoption.
- **A nimcrypto differential sweep during slices 1–2, while it is still
  resolvable.** (Round 2, considered and declined — previously not
  recorded at all.) It would be strictly cheap (same language, no FFI
  wrapper, deleted with the dep at slice 3(f)), and it is the one
  instrument that becomes permanently impossible after removal. Declined
  because its evidence is subsumed on both axes: correctness weight is
  carried by CAVP (the richer corpus) plus libsodium (an independently
  audited oracle — which nimcrypto is not; agreement with the code being
  replaced proves continuity, not correctness), and continuity on every
  production input shape is already enforced transitively by the
  zero-vector-change gate (every RFC 8032 KAT transits SHA-512
  end-to-end). A transient oracle adding no assurance the permanent ones
  lack is scope, not signal.
