### X25519 three-role batch summary (revisits ledger #29 from wontfix to fixed, 2026-08-06)
Not a review finding — an approved API redesign, done via strict TDD (RED-GREEN-REFACTOR, one behavior at a time, tests run every cycle). Ledger #29 (X25519Key's one-type-three-roles gap: same-role argument swaps like `x25519(secret, secret)` still compiled) was originally recorded `wontfix` in B5 because a three-way split was "ceremony without closing a real distinction." Corey's direction reopened it: split anyway, because the real gap isn't the same-role swap specifically, it's that one type let SECRET material (a private scalar, a DH output) and SENDABLE material (a public u-coordinate) be confused for each other with no compiler signal — encoding "same wire format" as "same type" was never required by RFC 7748 itself.

- **THE empirical verification the mission called out as the one real risk (sink + move-only single-use enforcement): CONFIRMED WORKING**, with one significant, load-bearing refinement discovered along the way, backed by isolated scratch probes (a minimal standalone type, unrelated to sello, built specifically to isolate Nim's ownership behavior from sello's own code):
  - **The core guarantee holds exactly as specified.** A genuinely unadorned reuse — `x25519` called twice on the same `X25519EphemeralSecret` variable, no `move()` anywhere — fails to compile (`reject_ephemeral_reuse.nim`, confirmed by direct `nim c` before the test wrapped it: `requires a copy because it's not the last read of 'eph'`, and `=copy` is `{.error.}` so the required copy cannot be synthesized). A direct copy (`var b = a`) fails identically (`reject_ephemeral_copy.nim`). Both are raised by the `injectdestructors` pass, later in the pipeline than `compiles()`/`nim check` reach — exactly the class of violation `Keypair`'s own copy fixture already established needs a real subprocess `nim c`, not a `compiles()` wrapper, to observe.
  - **Unanticipated finding: Nim's sink-argument "last read" inference is a simple per-symbol occurrence COUNT over the whole scope, not an escape/alias analysis.** The mission's own approved design says `x25519Base`'s plain by-value parameter is "a borrow for non-last-use; the Keypair-by-value precedent" and implies the natural `x25519Base(eph)` then `x25519(eph, peer)` sequence should compile unaided. It does not: once `eph` has ANY earlier reference in scope — the `x25519Base` borrow, but also (isolated scratch probes confirmed) a bare `addr eph`, a bare field read `eph.bytes[0]`, or even a `var`-parameter borrow — the LATER `x25519(eph, peer)` sink call fails with the identical `'=dup' is not available ...; requires a copy because it's not the last read` error, because Nim's analysis is a textual occurrence count, not a proof that the earlier reference left no live alias. The `Keypair`-by-value precedent this design leaned on never actually exercised this combination: every existing `Keypair` call site reads it repeatedly but never subsequently moves it via `sink`, so the precedent's "borrows are free" observation is true but incomplete — it holds only when the variable is NEVER later sink-consumed in the same scope. The fix, once found, is Nim's own standard idiom: wrap the argument in `system.move` (`x25519(move(eph), peer)`), which requires `eph` be declared `var` (`move` takes `var T`) and explicitly overrides the compiler's conservative analysis. A genuinely sole, single-use consuming call (no earlier reference at all) needs no `move()` — confirmed both by the reject-reuse fixture's own accepted FIRST call and by an isolated probe. A second, related surprise: Nim's `unittest.test` template wraps every test body in an implicit `try`/`finally`, and a `try` block's own exception-edge destructor obligation means even a SOLE sink-consuming use *inside a test* needs `move()` too (isolated probe confirmed this independent of sello's types) — so every consuming call in `test_x25519.nim`/`test_facade.nim` uses `move()`, even the ones demonstrating the "single-use needs no move()" claim, which is instead demonstrated by the fixture's own plain top-level (non-test, non-try) code.
  - **Honest residual gap, inherent to Nim's ownership model, disclosed rather than hidden:** `move()` is an explicit override of the compiler's static analysis. A caller who writes `move(secret)` at TWO separate consuming call sites for the same variable (rather than the natural unadorned-reuse pattern the fixtures cover) would compile — the second call would silently run on the wiped-to-zero, moved-from bytes instead of being rejected (confirmed via an isolated probe: two `move()` calls on the same var both compile and run, no error). This is not a sello-specific hole; it is what `system.move` means in Nim generally, on ANY move-only ARC/ORC type. Every legitimate call site in this codebase's own tests and the shipped doc examples use the natural pattern (`move()` appears exactly once per ephemeral variable, at its one true consuming call), so this gap describes a hypothetical misuse pattern, not anything this batch's own shipped code does. Documented in `x25519.nim`'s doc comment on the `sink` overload, `CLAUDE.md`, and `CHANGELOG.md` rather than glossed over — **this is not a blocker**: the mission's actual bar (an unadorned, natural reuse must be a compile error) is met and fixture-verified; what's disclosed here is a scope boundary on that guarantee, not a failure of it.
  - **This is NOT the blocker case the mission flagged** ("if sink+move-only does NOT produce the reuse compile error... STOP and report a BLOCKER") — the reuse error fires exactly as required for the case that matters (no explicit `move()`). What required investigation was the opposite direction: making the LEGITIMATE non-consuming-then-consuming sequence compile at all, which needed the `move()` idiom the mission's design text hadn't anticipated. Surfaced, understood via isolated reproduction, fixed, and documented — not silently patched over.
