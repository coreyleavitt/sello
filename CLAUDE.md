# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`sello` is a **pure-Nim Curve25519 library** (ed25519 EdDSA + X25519 ECDH) with **no FFI** in the core. It exists because the Nim ecosystem had no production pure-Nim 25519 — every other option wraps orlp's C. SHA-512 is the one dependency we do *not* reimplement; it comes from `nimcrypto`, resolved (not vendored) and pinned by commit SHA + content hash in `milpa.lock`. See `prompt.md` for the full design brief and rationale — it is the authoritative spec, and current code is a partial implementation of it.

## The load-bearing design decision: VERIFY is split from SIGN

This split drives the whole API and trust story — preserve it:

- **Verification** (`ed25519.verify`) touches only public data (pubkey, message, signature). It has **no constant-time requirement**, is fully testable, and is the part that ships to everyone with no asterisks. `scalarmultVartime` in `scalar.nim` uses plain 4-bit windows precisely because it only ever runs on the verify path — **do not add the signer's secret scalar to it**, and don't let it lose the `Vartime` suffix (RFC-001 finding 8: it used to be plain `scalarmult`, indistinguishable at call sites from the CT signer code sharing the file). As of round-3 finding A3 this is also a COMPILE error, not just a naming convention: `scalarmultVartime` accepts only a bare `array[32, byte]`, while the signer's secret scalar is typed `scalar.SecretScalar` from the moment it is assembled in `private/backend.nim` — passing one where the other belongs is an ordinary type mismatch (pinned by `tests/unit/fixtures/reject_secretscalar_vartime.nim`). `verify` has no backend dispatch and stays pure-Nim even under `-d:selloLibsodium`.
- **Signing / keygen** (`signing.nim` + `private/backend.nim`) holds the secret scalar → **is constant-time**: `{.push checks: off.}` cores, secrets confined to fixed-size stack arrays, every secret-dependent selection done by arithmetic masking (never a branch), and volatile-store-plus-barrier wiping (`private/ct.nim`) of every secret — including intermediate SHA-512 state — as soon as it's no longer needed. It carries the roll-your-own-crypto trust tax, backed by a dudect timing harness (`tests/ct/`, see below) and an **optional libsodium FFI adapter behind `-d:selloLibsodium`** (`private/backend_sodium.nim`) exposing the identical `Keypair` API.
- **X25519** (`x25519.nim`) also holds a secret (the caller's private scalar). Its Montgomery ladder is branchless on secret data (masked `feCSwap`, `{.push checks: off.}`, stack-only arrays, `private/ct.nim` wipe of every secret-derived intermediate after use — the clamped scalar copy, the ladder's own accumulators/temporaries, and the raw DH output, as of round-3 finding A1; previously only the clamped scalar copy was wiped).

## Architecture (bottom-up layering)

`src/sello.nim` is the public facade — the supported API surface (`verify`, `x25519`, `x25519Base`, `x25519StaticSecret`, `x25519StaticPair`, `x25519EphemeralSecret`, `x25519EphemeralPair`, `keypair`, `sign`, `Seed`/`Keypair`/`toSeed`/`toSeedBytes`/`wipe` (`toSeedBytes`: renamed from `toBytes` by round-3 finding A7 -- every other `toBytes` in this codebase serializes its own type's identity, but this one returns the keypair's SEED, which the old name didn't signal), and the nominal key/signature types `PublicKey`/`Signature`/`X25519StaticSecret`/`X25519EphemeralSecret`/`X25519Public`/`X25519Shared` plus their `toPublicKey`/`toSignature`/`toX25519StaticSecret`/`toX25519Public`/`toBytes` converters). As of RFC-004 slice 8d, also the ristretto255 surface, ENUMERATED symbol-by-symbol matching this file's own precedent: `RistrettoPoint`/`RistrettoEncoded`/`RistrettoStaticSecret`/`RistrettoEphemeralSecret`, `RistrettoIdentity`/`RistrettoBasePoint`, `ristrettoDecode`/`ristrettoEncode`, the group operators `+`/binary `-`/unary `-`/`==` (this codebase's first operators), `ristrettoScalarmultBase`/`ristrettoScalarmult`/`ristrettoScalarmultVartime`, `ristrettoFromUniformBytes`, `ristrettoStaticSecret`/`ristrettoStaticPair`/`toRistrettoStaticSecret`/`toRistrettoStaticSecretWide`/`ristrettoEphemeralSecret`/`ristrettoEphemeralPair`/`toRistrettoEncoded`/`toBytes`/`wipe`/`$`/`hash` (`ristretto.nim`'s own module doc comment and its list below have the full rationale; `ristrettoUnchecked` and `scalar.SecretScalar` are deliberately NOT exported). Consumers `import sello`; submodules are importable but carry no stability promise.

Modules under `src/sello/`, each built strictly on the one(s) below (with one standing exception: `private/ct.nim` is a universal leaf that secret-holding modules at any position reach into directly, regardless of list order):

1. **`field.nim`** — GF(2²⁵⁵−19) arithmetic. Radix 2²⁵·⁵, 10 `int32` limbs (`Fe` object). Direct ref10/orlp port (public domain). All the `fe*` primitives: mul, sq, invert, `fePow22523`, encode/decode, canonicity check (`feBytesCanonical`), constant-time `feCMove`/`feCSwap`, and `clampScalar` (shared by ed25519 and X25519 clamping — lives here so `x25519.nim` stays a `field.nim`-only consumer). Also `feFromLimbs` (RFC-003 slice 1: the one audited construction door for limb-built `Fe`s — `Fe.limbs` stays public for the arithmetic core's hot-path mutation, but every constant-from-raw-array site goes through this except the trivial 0/1 constants `FeZero`/`FeOne` (`field.nim`), which construct `Fe(limbs: [...])` directly rather than through the door — matching `feFromLimbs`'s own doc comment, which is precise about this rather than claiming blanket coverage) and vartime `feSqrtRatioVartime` (the RFC 8032 §5.1.3 sqrt-ratio dance — candidate root, sqrt(-1) retry, reject — extracted from `ed25519.pointDecode` so a future Ristretto decode can reuse it without importing the verify module; the sqrt(-1) constant moved here from `scalar.nim` with it, now unexported, since it's a field-only property with no curve equation baked in).
2. **`wire.nim`** — leaf module (round-2 findings 27/28, split from the combined `types.nim` by RFC-002 slice 2 item 5): nominal wire types `PublicKey`/`Signature` (`distinct array[32/64, byte]`, RFC-001 finding 9) plus their `toPublicKey`/`toSignature`/`toBytes`/`==`/`$`/`hash` borrows — no crypto logic of its own, and (unlike the old combined module) no `private/ct` import either, since these types hold no secret to wipe. Relocated out of `scalar.nim`, which was holding these purely so `ed25519.nim` and `signing.nim` had a shared downward import; that polluted `scalar.nim`'s group-ops mandate with wire-format/hygiene concerns its arithmetic never touches. `ed25519.nim` (verify) and `signing.nim` (sign) both depend on `wire.nim` directly now; `ed25519.nim` still re-exports the types so `import sello/ed25519` alone finds them (preserved compatibility).
   **`wipe.nim`** — the other half of the old `types.nim` split (RFC-002 slice 2 item 5): the generic secret wipe `wipe*(var array[32, byte])` (RFC-001 finding 11), delegating to `sello/private/ct` (a leaf itself). `types.nim`'s own doc comment had admitted the wire types and this wipe shared that module for import-graph position only, not a common purpose ("two leftover leaf concerns, one roof"); splitting gives each its own single-purpose roof.
   **`challenge.nim`** — the ed25519 challenge hash `challenge(R, A, msg)` (RFC 8032 §5.1.6 step 4 / §5.1.7 step 2), extracted out of `scalar.nim` by RFC-002 slice 2 item 1: it was the one thing in that file pulling in nimcrypto's SHA-512. Imports `sello/scalar` (for `scReduce`) and `nimcrypto/sha2`; consumed by `ed25519.nim` (verify) and `private/backend.nim` (sign) — one audited copy of the formula shared by both, so sign/verify can never silently drift apart.
3. **`scalar.nim`** — Curve25519 group ops in extended Edwards coordinates (`GeP3`/`GeP2`/`GeP1P1`/`GeCached`). Point add/double, variable-base `scalarmultVartime` (verify-only, vartime — named with the suffix, RFC-001 finding 8, so it self-flags at every call site instead of relying on a doc comment to distinguish it from the CT signer code sharing this file), and fixed-base `geScalarmultBase` (signed radix-16 digits over a compile-time `GeCached` base table, CT `cmovCached` select — used by both keygen and signing, safe on secret scalars; a debug-only `assert` here checks its bit-255-clear precondition, wrapped in `when not defined(release)` so the dudect-measured build is untouched — plain `assert` alone does NOT get stripped by `-d:release` in this Nim 2.2.10 config, empirically verified, contrary to the RFC's stated assumption; see the assert's own comment). Also declares `SecretScalar` (round-3 finding A3: `distinct array[32, byte]`, no converter to/from a bare scalar array) — the type-level gate that makes "a secret scalar can never reach `scalarmultVartime`" a compile error rather than a naming convention; `geScalarmultBase` and `scMulAdd`'s two secret-scalar parameters accept only `SecretScalar`, `scalarmultVartime` accepts only `array[32, byte]`, and `private/backend.nim` is the one caller that constructs one (see that module and `SecretScalar`'s own doc comment for the full home/scope reasoning, including why `x25519.nim`'s ladder and `recodeScalarRadix16` deliberately stay untyped byte-level code below this boundary). `scReduce`/`scIsCanonical`/`scMulAdd`/`pointEncode` also live here (moved down from `ed25519.nim` so the signing backend never imports the verify-only module); the shared `challenge(R, A, msg)` hash that used to live alongside them moved out to `challenge.nim` (above) in RFC-002 slice 2, taking this file's only nimcrypto import with it — `scalar.nim` is now a pure field-plus-curve-math leaf with no nimcrypto dependency. Curve constants (`Ed25519D_Raw`, `Ed25519Gx/Gy_Raw`) live here too (`SqrtM1_Raw` moved to `field.nim` as `feSqrtRatioVartime`'s private constant — RFC-003 slice 1; it's a field property, not a curve one). `geSub` (dead ref10-port residue, zero call sites) was deleted in the same slice. Back to pure group ops as of round 2 — the wire types it used to hold moved to `wire.nim` (above).
4. **`ed25519.nim`** — RFC 8032 layer: `pointDecode` (strict §5.1.3: rejects y ≥ p and x=0-with-sign-bit) and `verify` (`openArray[byte]` and `string` overloads, taking the nominal `Signature`/`PublicKey` from `wire.nim`). Verify-only, never touches a secret, no backend dispatch — pure-Nim always, including under `-d:selloLibsodium`.
5. **`x25519.nim`** — RFC 7748 layer on `field.nim` only (no Edwards code): Montgomery ladder (branchless on the secret scalar, `private/ct.nim`-wiped after use), `x25519` (returns `none` on all-zero shared secret, i.e. small-order peer point) and `x25519Base`. Role-typed wrappers, one per X25519 role, not one type for all three (RFC-001 ledger #29, revisited on Corey's direction — supersedes finding 9's original one-`X25519Key` design), and the SECRET role is itself split in two (the X25519 static/ephemeral batch, closing the deferral this list used to record): `X25519StaticSecret` (a reusable private scalar; one-field object, not `distinct array`, for the same empirically-established reason `signing.Seed` isn't — see its doc comment — `=destroy`-wiped, deliberately copyable like `Seed`, every copy self-wipes independently), `X25519EphemeralSecret` (a SINGLE-USE private scalar, x25519-dalek's `EphemeralSecret` in this module's own vocabulary: move-only — `=copy {.error.}`, the `Keypair` pattern — constructed ONLY via `x25519EphemeralSecret()` (fresh from `std/sysrand`, no from-bytes route: freshness by construction), with NO `toBytes` either (unpersistable by design); `x25519Base(secret: X25519EphemeralSecret)` is a non-consuming plain-value borrow, `x25519(secret: sink X25519EphemeralSecret, peer)` CONSUMES it — `sink` plus the move-only `=copy` error together make reuse a compile error, fixture-verified (`tests/unit/fixtures/reject_ephemeral_reuse.nim`, `reject_ephemeral_copy.nim`, driven by subprocess `nim c` in `test_x25519.nim` — `compiles()`/`nim check` cannot see this error class, same reason as `Keypair`'s copy fixture) rather than a documented caller obligation), `X25519Public` (a public u-coordinate; plain `distinct array[32, byte]`, freely copyable, no destructor), and `X25519Shared` (a completed DH output; same shape as `X25519StaticSecret`, since it IS secret material). RFC 7748 does treat all three wire roles as the identical 32-byte format, and one type for all of them closed the cross-algorithm mixup (`verify(sig, msg, x25519Key)`) at zero ergonomics cost — but it also meant role confusion between secret and sendable X25519 material failed open, and gave no way to express "this secret must not outlive one exchange." Splitting the secret role further mirrors `Seed`/`PublicKey` on the ed25519 side for the sendable/secret boundary, and closes the single-use gap the same way `Keypair`'s move-only `=copy` closes accidental duplication. **Empirical Nim-ownership finding, load-bearing for the ephemeral design (verified via isolated scratch probes on Nim 2.2.10/ORC, not assumed):** the sink-argument "is this the last read" check is a simple per-symbol occurrence count over the whole scope, not an escape/alias analysis — ANY earlier reference to the same variable (even a bare field read or `addr`, confirmed directly), or the call merely sitting inside a `try`/`finally` (which `unittest.test` wraps every test body in), makes a later bare `x25519(secret, peer)` require a copy it cannot make; the caller must use `system.move` (`x25519(move(secret), peer)`, which needs `secret` declared `var`) whenever `x25519Base` (or anything else) touched the same variable first. A genuinely sole, un-annotated consuming call needs no `move()` — ordinary last-use inference already covers it (see `x25519.nim`'s doc comment on the `sink` overload for the full writeup, including the honest residual gap: `move()` is Nim's own explicit override of this analysis, so a caller who writes it at two separate consuming call sites for the same variable would compile — the natural, unadorned reuse pattern the negative fixtures actually cover remains correctly rejected). All types stay in `x25519.nim` rather than moving to `wire.nim`: they are RFC 7748's own types, with no consumer outside this module's own RFC 7748 layer, unlike `PublicKey`/`Signature`, which two separate upward modules needed to share. Also exports `toX25519StaticSecret`/`toX25519Public`/`toBytes`/`x25519StaticSecret()`/`x25519StaticPair()` (RFC-003 slice 1: bundled fresh-secret-plus-public constructor for the static role, mirroring `x25519EphemeralPair()`'s shape — a full `Keypair`-style invariant object was considered and declined since X25519 ops take only the secret)/`x25519EphemeralSecret()`/`x25519EphemeralPair()` and the `X25519StaticSecret`/`X25519EphemeralSecret`/`X25519Shared`-typed `wipe` overloads (RFC-001 finding 11) that give callers holding X25519 secret material outside a `Keypair`/`Seed` a supported route to `private/ct.wipe`; the generic `array[32, byte]` `wipe` overload lives in `wipe.nim` (round-2 finding 28, its own leaf as of RFC-002 slice 2), not here, since it isn't X25519-specific.
6. **`ristretto.nim`** — the ristretto255 prime-order group (RFC 9496, RFC-004), built on `field.nim` + `scalar.nim` only — a sibling of `x25519.nim` in the layering, below `ed25519.nim`/`signing.nim`, above the field/curve core; never imports the verify-only module, `challenge.nim`, or a backend, and stays nimcrypto-free (hash-to-group takes 64 caller-hashed bytes, per RFC 9496 §4.3.4 leaving the hash out of scope). Internally it IS the existing extended-Edwards arithmetic (`GeP3` add/double/scalarmult reused unchanged) wrapped in an encode/decode/equality/map layer that quotients away the cofactor-8 ambiguity a raw `GeP3` carries — every `RistrettoPoint` names one group element with exactly one canonical 32-byte encoding (`RistrettoEncoded`). **CT posture (load-bearing, mirrors the VERIFY/SIGN split's own care but cuts across it differently):** decode/encode/equality/the map are CT by construction (straight-line field arithmetic plus `feCMove`-based selects); the final accept/reject verdict (`ristrettoDecode`'s `none`, `==`'s result) is inherently caller-visible and carries no CT obligation of its own. This diverges from `ed25519.verify`'s "no CT requirement at all" posture because ristretto255 elements are routinely *derived from* secrets in the protocols this module serves (a Pedersen commitment before publication, an OPRF blinded element, a DH share) even though the encoding eventually goes on the wire. `RistrettoPoint`'s `==` is therefore CT (the one `==` in this codebase that is, diverging deliberately from `wire.nim`'s vartime register); `RistrettoEncoded`'s `==` stays the ordinary vartime byte-compare, an intentional split an operator cannot self-flag (no `Vartime` suffix on an operator) — see the module's own doc comment and README's Ristretto255 section for the encode-then-compare timing trap this creates. New CT field primitives back this (`field.nim`): `feSqrtRatioM1` (RFC 9496 §4.2's three-check `SQRT_RATIO_M1`; `ed25519.pointDecode` was REWRITTEN onto it and the old vartime `feSqrtRatioVartime` DELETED — two independently-maintained sqrt-ratio implementations in one codebase is exactly the drift mode `challenge.nim` exists to kill), `feEqualCT`/`feIsZeroCT`/`feBytesCanonicalCT`, `feAbs`, and a re-exported `FeSqrtM1`. Scalar multiplication ships in both registers behind the same `SecretScalar` type gate the rest of the codebase uses: `ristrettoScalarmultVartime` (bare `array[32, byte]` only, a secret scalar cannot reach it — a compile error, not a convention) and, on the secret-scalar side, `ristrettoScalarmultBase` (CT fixed-base, over the existing `geScalarmultBase`) plus `ristrettoScalarmult` (CT variable-base, over new `scalar.geScalarmultCT` — a uniform 256-doubling interleaved radix-16 ladder with a runtime 8-entry `GeCached` table, NOT a clone of `geScalarmultBase`'s odds/×16/evens shape, which only works for a table pre-scaled by 16^(2j); the operation that makes the group usable for OPRF evaluation, Pedersen commitments, and DH shares over an arbitrary point, R1-wipe-disciplined throughout). Two secret-scalar role types mirror X25519's static/ephemeral split: `RistrettoStaticSecret` (reusable — a Pedersen key, an OPRF server key; copyable, self-wiping, always a canonical residue mod L, `toRistrettoStaticSecret` REJECTS non-canonical import while `toRistrettoStaticSecretWide` totally reduces — named distinctly, not overloaded by array length, since reject-vs-reduce is a security-semantic difference) and `RistrettoEphemeralSecret` (single-use, move-only — an ElGamal/ECIES-style one-shot DH share: ephemeral k, `C1 = ristrettoScalarmultBase(k)` borrowed and sent, then `S = k·P` via the ONE consuming `ristrettoScalarmult(sink ..., ...)` call, k dead thereafter; a CPace-style PAKE's two-mults-one-scalar shape does NOT fit this type by design and routes to `RistrettoStaticSecret` + `wipe` instead, documented as the honest boundary rather than a defect). `RistrettoPoint` itself is freely copyable with deliberately NO `wipe` overload and NO `hash` overload: elements are PUBLIC-register values in every protocol this serves (the published commitment/blinded element/DH share is never itself the secret — the scalar that derived it is, and that scalar's role type owns the hygiene), and a hash must agree with `==`, which only the canonical encoding (`RistrettoEncoded`, which DOES have `hash`) guarantees across representations — key/dedupe on the encoding, never the point. **Non-goal, stated honestly rather than left implicit:** this module ships the GROUP, not a scalar-arithmetic API — a Schnorr response needs `scalar.scMulAdd` (exists, submodule-only, deliberately not facade-exported, since exporting it would drag the bare hygiene-free `scalar.SecretScalar` into the public surface); an OPRF CLIENT's unblind step needs mod-L scalar inversion, which exists NOWHERE in sello at any layer (`field.feInvert` is mod-p field inversion, unrelated) — so v1 serves commitment/DH/blinding-shaped protocols and an OPRF SERVER's evaluation step, not an OPRF client or a Schnorr prover. Facade-exported (`src/sello.nim`) as an ENUMERATED symbol list, matching that file's own precedent; `ristrettoUnchecked` (the module's one `feFromLimbs`-style raw-`GeP3` construction door, used by this module's own constructors/group ops and `test_ristretto.nim`'s white-box oracles) and `scalar.SecretScalar` are deliberately NOT among the exports.
7. **`signing.nim`** — `Seed`/`Keypair` types (fields private, move-only `Keypair`, `=destroy` wipes), the `keypair(seed)`/`keypair()` constructors, `keypair(seed, expectedPublic): Option[Keypair]` (janus consumer finding 2 — the load-time gate for persisted keys whose storage carries both halves, e.g. OpenSSH's/libsodium's `seed(32) ‖ publicKey(32)` layout: re-derives the public key and returns `none` on mismatch, because sello's re-derivation otherwise makes a corrupted stored key fail OPEN — it signs successfully under a public key the caller never presented; `Keypair` being move-only, the extraction idiom is `move(loaded.get())` via the `var Option` `get` overload), `sign`, and the `when defined(selloLibsodium)` backend dispatch (`private/backend_sodium` vs. `private/backend`, bound to one local name so every call site is backend-agnostic; that backend's `SodiumInitError` is re-exported here and through the facade under the flag, since it now appears in declared `{.raises.}` effects). Depends on `wire.nim` directly for `PublicKey`/`Signature` (not `ed25519.nim` — signing has no business importing the verify-only module; not `scalar.nim` either, since round 2 moved those types out of it). The facade re-exports from here with no conditional logic of its own.
8. **`private/backend.nim`** — the pure-Nim secret-math backend: seed-level `derivePublic`/`signDetached`, no `Keypair` knowledge. Builds on `field.nim` + `scalar.nim` + `challenge.nim` + nimcrypto SHA-512 only. Under `private/` because its exports bypass every `Keypair` guarantee (no invariant, no auto-wipe) — application code should use `sello.keypair`/`sello.sign`, never this module directly. `signDetached` carries a debug-only `assert` (RFC-002 slice 2) re-deriving and checking the caller-supplied public key against the secret scalar — expensive on purpose, wrapped in `when not defined(release)` (not a bare `assert`) so it is entirely absent from the dudect-measured/shipped release build.
9. **`private/backend_sodium.nim`** — the libsodium FFI adapter (only compiled under `-d:selloLibsodium`), mirroring `backend.nim`'s exact seed-level contract via `crypto_sign_seed_keypair`/`crypto_sign_detached`; atomic `sodium_init` once-guard (`std/atomics`, not a plain check-then-set flag). Also carries four ristretto255 oracle wrappers (RFC-004 slice 8c: `sodiumRistrettoIsValidPoint`/`sodiumRistrettoFromHash`/`sodiumRistrettoScalarmult`/`sodiumRistrettoScalarmultBase`) plus `sodiumLibraryVersion` — differential-test oracles ONLY, never wired into `signing.nim`'s dispatch (Ristretto has no backend-dispatch story of its own; see `ristretto.nim`'s own non-dispatch design and RFC-004's Non-goals), consumed exclusively by `test_libsodium_interop.nim` behind a runtime libsodium >= 1.0.18 version assert (the first version-sensitive API this file wraps).
10. **`private/ct.nim`** — the one audited secret-wipe primitive (`wipe[T]`: volatile per-byte stores + `asm volatile("" ::: "memory")` barrier, `{.noinline.}`), called from `backend.nim`, `x25519.nim`, `wipe.nim`, `ristretto.nim`, and (as of round-3 finding A5) `private/secret_hooks.nim` — a small `{.dirty.}`-template pair (`secretHooks`/`secretHooksMoveOnly`) that emits the `zeroize<Type>`/`=destroy`/optional `=copy {.error.}` boilerplate once, instantiated by `signing.nim` (`Seed`), `x25519.nim` (`X25519StaticSecret`/`X25519EphemeralSecret`/`X25519Shared`), and `ristretto.nim` (`RistrettoStaticSecret`/`RistrettoEphemeralSecret`) in place of hand-copied versions of the same shape. `Keypair`'s own `=copy {.error.}` stays hand-written (no `bytes` field of its own to wipe — see the template module's doc comment).

`tests/ct/` (`dudect.nim` + `ct_main.nim`) is the dudect-style timing harness, run via `scripts/ct.sh` — see below.

## Building & testing

**milpa** (Corey's Nim dependency resolver, `~/.local/bin/milpa`) is the authoritative resolver for development — not nimble. It reads `milpa.kdl`, clones deps into `_deps/` (content-addressed under `~/.cache/milpa`, gitignored), and writes `milpa.lock` (commit SHA + dag-sha256 content identity + provenance per dep — that's how nimcrypto is pinned; see NOTICE). Run `milpa fetch` once after cloning (and again after editing `milpa.kdl`) to populate `_deps/` and emit `nim.cfg`.

There is **no host Nim toolchain** in this environment; all builds happen in the base toolchain image. `scripts/test.sh`, `scripts/test-libsodium.sh`, and `scripts/ct.sh` (replacing the old nimble tasks) wrap the exact podman invocation, mounting the project plus the milpa CAS at both its canonical path and its host-absolute path (so milpa's absolute dep symlinks under `_deps/` resolve in-container).

`Containerfile.amox` is **amoxtli's sandbox image**, unrelated to sello (its package list — rust/go/node/openssl — belongs to a different project entirely); do not confuse the two or bolt sello-specific packages onto it. sello owns a minimal `Containerfile` of its own (`FROM ghcr.io/coreyleavitt/nim:2.2.10` + `libsodium-devel` + `z3-devel`), built as the `sello-dev` image and used by both `scripts/test-libsodium.sh` (libsodium adapter matrix) and `scripts/bmc.sh` (Z3-backed symex proof, RFC-001 finding 22) — one image covers both, rather than maintaining near-duplicate layers. `scripts/test.sh`, `scripts/ct.sh`, and `scripts/fuzz.sh` need neither this image nor network access.

**proptest** (property-based testing, RFC-001 finding 10) is an *optional* milpa dep: `milpa.kdl` declares it `optional=#true`, which milpa desugars into an auto-flag named `proptest` (default off) gating the dep — so `milpa fetch` alone (what a downstream consumer of sello runs) never fetches proptest or its own transitive deps (`nim-z3`, `softlink`; proptest's manifest depends on `nim-z3` unconditionally). To build/run the property tests, fetch it explicitly once: `milpa fetch --features proptest` (root-level `--features` flag, RFC #23 §3.4) — this populates `_deps/proptest`, `_deps/z3`, `_deps/softlink` and adds their `--path` lines to `nim.cfg`. `import proptest` compiles and links fine in the base image with no z3 shared library installed: the only proptest module that imports `z3` is `proptest/symex`, which the top-level `proptest` module never imports (confirmed empirically, not merely by reading the source). Re-running a plain `milpa fetch` afterwards prunes proptest back out (activation is recomputed from the manifest + requested features every fetch, not preserved from the lock) — this also means `milpa.lock`'s proptest/z3/softlink entries come and go with which fetch you last ran; that's expected, not a hygiene problem.

`milpa fetch` emits `nim.cfg` **wholesale** (`--path:"src"` + one `--path` per resolved dep) — it owns that file entirely and rewrites it on every fetch, so nothing else may live there. The project-standing `--mm:orc`/`--outdir:"build"` flags instead live in root `config.nims` (`switch("mm","orc")`, `switch("outdir","build")`), a file milpa never touches; Nim reads both `nim.cfg` and `config.nims` for every invocation, so the two compose without conflict. `build/` is gitignored — never commit binaries. `nim.cfg` and `_deps/` are also gitignored (regenerated by `milpa fetch`); `milpa.kdl` and `milpa.lock` ARE committed.

  - `symex_mask.nim` — `field.feCMove`/`feCSwap`'s arithmetic-masking algebra (the constant-time selection primitive every secret-dependent choice in this codebase routes through). Proves, as THREE separate `sxUnsat` `symexFind` queries (a tooling-forced split — a branch-merged `int32` local crashes the walker when fed into a binop alongside another symbolic value, a third empirical symex limitation joining `symex_recode.nim`'s two, documented in this file's own module doc comment): (1) `maskConstructStep` — the mask construction (`-int32(b)`, re-encoded as `if b: -1'i32 else: 0'i32` and cross-checked equivalent) yields exactly `0` or `-1`, for both booleans; (2)/(3) `cmoveSelectStep`/`cswapSelectStep` — GIVEN a mask already known to be `0`/`-1` (a free parameter, not derived from a bool in the same proc), the masked-XOR select/swap is exactly correct, over the FULL `int32 x int32` domain per boolean (Z3 bitvector theory decides this exactly, not sampled). Because `feCMove`/`feCSwap` apply this one-limb formula independently to each of `Fe`'s 10 limbs with no inter-limb dependency, the one-limb verdicts already cover the whole 10-limb function — no separate whole-loop composition query is needed. `crossCheckMaskConstructThenSelect` chains the three lemmas back together (the real functions' own construct-then-consume order) and confirms the split reproduces `feCMove`/`feCSwap`'s concrete behavior on 1124 boundary-plus-random cases.
  - `symex_equal.nim` (RFC-004 slice 1b) — the shared or-accumulate shape of `field.feEqualCT`/`feIsZeroCT`/`feBytesCanonicalCT` (the CT equality/canonicity primitives backing ristretto255's decode/encode/`==`): one `sxUnsat` lemma, full-domain over symbolic bytes, proving the accumulated word is zero iff every byte pair is equal. A fourth empirical symex-walker limitation was found and documented in the same slice, joining `symex_recode.nim`'s two and `symex_mask.nim`'s third: a literal-seeded accumulator chain crashes the walker, worked around by seeding from the first byte pair's own xor instead of a literal zero.
  - `symex_reduce.nim` — the carry-propagation macro shared by `scalar.scReduce` and `scalar.scMulAdd` (both port the same ref10 reduction routine, appearing in BIASED (`carry = (s + 2^20) shr 21`) and UNBIASED (`carry = s shr 21`, final passes only) variants). `carryMacroBiasedStep`/`carryMacroUnbiasedStep` are full-domain `sxUnsat` proofs (each well under 0.1s) that either macro, applied to ANY `int64` within a generously justified `|s| < 2^61` envelope (see the module doc's INPUT BOUND DERIVATION, `arithChecks = {}` needed both for query cost and to keep an unconstrained companion parameter from tripping a genuine-but-out-of-scope overflow defect), lands the output in its documented canonical range ([-2^20, 2^20) biased, [0, 2^21) unbiased) — a full-domain proof of the "per-step bound invariant... no overflow" property directly. Two further compositions (`scReduceCarryChainFreeVars`, transliterating `scReduce`'s ENTIRE body with `s0..s23` as free parameters instead of byte-array-decoded, which — unlike `symex_recode.nim`'s free-nibble generalization — would close the literal-function gap directly since the parameter domain IS the real decoded domain; and `scMulAddCarryChainFreeVars`, the analogous carry-chain-tail-only composition, deliberately excluding the nonlinear multiply pyramid feeding it, whose own magnitude bound is instead a **written argument**, not machine-checked, given the up-front cost asymmetry between constant-multiply and symbolic×symbolic multiply) were ATTEMPTED against real Z3 and hit a genuine RESOURCE WALL — no verdict within ~515s and ~550s of isolated solver time across two runs, the same "resource exhaustion, not infeasibility" outcome `symex_recode.nim`'s original whole-byte-array attempt hit. Per that file's own precedent (don't chase an ever-larger timeout), both compositions are gated behind `-d:selloBmcReduceFullChain` (OFF by default, not part of `scripts/bmc.sh`) and reported honestly as attempted-and-inconclusive, not claimed. Both transliterations ARE exercised, always, by fast concrete cross-checks confirming byte-exact agreement with the real `scReduce`/`scMulAdd` on boundary-plus-random vectors — so the per-step lemmas are the tractable machine-checked result for this property; the full-function composition remains a documented open question, not a silent gap.

## Conventions
- Port from permissively-licensed references (ref10/djb, TweetNaCl, orlp) and **attribute in the module header** as existing files do. Get functional correctness against vectors first, then CT-harden the signer.
- **Effects are declared, not inferred** (janus consumer finding 3): every `src/sello/` module carries `{.push raises: [], gcsafe.}` (the five `std/sysrand` fresh-secret constructors override with explicit `{.raises: [OSError].}`; `signing.nim`'s push and `keypair()` region widen by `SodiumInitError` under `-d:selloLibsodium`, matching `backend_sodium.nim`'s own push). New procs land under the nearest push automatically — if one genuinely must raise, give it an explicit per-proc annotation (or its own push/pop region, the `keypair()` precedent) rather than widening a module-level push. Pinned by `test_facade.nim`'s "declared effect contract" suite, which fails to compile if a declared effect grows.
- Secrets (signing, X25519 scalars): fixed-size stack `array[N, uintXX]`, never `seq`/`string`; zero allocation in the hot path.
- Scratch/diagnostic files from debugging sessions do not get committed — the maintained suite lives in `tests/unit/`, and `build/` catches binaries.
