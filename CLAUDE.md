# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`sello` is a **pure-Nim, zero-dependency Curve25519 library** (ed25519 EdDSA + X25519 ECDH) with **no FFI** in the core. It exists because the Nim ecosystem had no production pure-Nim 25519 — every other option wraps orlp's C. SHA-512 (ed25519's internal hash) was originally sourced from `nimcrypto`; as of RFC-006 it is in-house (`src/sello/private/sha512.nim`, FIPS 180-4, validated against the full NIST CAVP SHAVS corpus), and `nimcrypto` is no longer a dependency at all — a plain `milpa fetch`/`nimble install` resolves zero dependencies, with `proptest` remaining as an *optional*, dev-only dependency for property-based testing (see "Building & testing" below). See `prompt.md` for the full design brief and rationale — it is the authoritative spec (subject to RFC-006's in-place amendments, dated and noted in that file), and current code is a partial implementation of it.

## The load-bearing design decision: VERIFY is split from SIGN

This split drives the whole API and trust story — preserve it:

- **Verification** (`ed25519.verify`) touches only public data (pubkey, message, signature). It has **no constant-time requirement**, is fully testable, and is the part that ships to everyone with no asterisks. `scalarmultVartime` in `scalar.nim` uses plain 4-bit windows precisely because it only ever runs on the verify path — **do not add the signer's secret scalar to it**, and don't let it lose the `Vartime` suffix (RFC-001 finding 8: it used to be plain `scalarmult`, indistinguishable at call sites from the CT signer code sharing the file). As of round-3 finding A3 this is also a COMPILE error, not just a naming convention: `scalarmultVartime` accepts only a bare `array[32, byte]`, while the signer's secret scalar is typed `scalar.SecretScalar` from the moment it is assembled in `private/backend.nim` — passing one where the other belongs is an ordinary type mismatch (pinned by `tests/unit/fixtures/reject_secretscalar_vartime.nim`). `verify` has no backend dispatch and stays pure-Nim even under `-d:selloLibsodium`.
- **Signing / keygen** (`signing.nim` + `private/backend.nim`) holds the secret scalar → **is constant-time**: `{.push checks: off.}` cores, secrets confined to fixed-size stack arrays, every secret-dependent selection done by arithmetic masking (never a branch), and volatile-store-plus-barrier wiping (`private/ct.nim`) of every secret — including intermediate SHA-512 state — as soon as it's no longer needed. It carries the roll-your-own-crypto trust tax, backed by a dudect timing harness (`tests/ct/`, see below) and an **optional libsodium FFI adapter behind `-d:selloLibsodium`** (`private/backend_sodium.nim`) exposing the identical `Keypair` API.
- **X25519** (`x25519.nim`) also holds a secret (the caller's private scalar). Its Montgomery ladder is branchless on secret data (masked `feCSwap`, `{.push checks: off.}`, stack-only arrays, `private/ct.nim` wipe of every secret-derived intermediate after use — the clamped scalar copy, the ladder's own accumulators/temporaries, and the raw DH output, as of round-3 finding A1; previously only the clamped scalar copy was wiped).

## Architecture (bottom-up layering)

`src/sello.nim` is the public facade — the supported API surface (`verify`, `x25519`, `x25519Base`, `x25519StaticSecret`, `x25519StaticPair`, `x25519EphemeralSecret`, `x25519EphemeralPair`, `keypair`, `sign`, `Seed`/`Keypair`/`toSeed`/`toSeedBytes`/`wipe` (`toSeedBytes`: renamed from `toBytes` by round-3 finding A7 -- every other `toBytes` in this codebase serializes its own type's identity, but this one returns the keypair's SEED, which the old name didn't signal), and the nominal key/signature types `PublicKey`/`Signature`/`X25519StaticSecret`/`X25519EphemeralSecret`/`X25519Public`/`X25519Shared` plus their `toPublicKey`/`toSignature`/`toX25519StaticSecret`/`toX25519Public`/`toBytes` converters). As of RFC-004 slice 8d, also the ristretto255 surface, ENUMERATED symbol-by-symbol matching this file's own precedent: `RistrettoPoint`/`RistrettoEncoded`/`RistrettoStaticSecret`/`RistrettoEphemeralSecret`/`RistrettoShared` (the wiped DH-share output type added by the RFC-004 stage-4 review — the consuming ephemeral `ristrettoScalarmult` returns `Option[RistrettoShared]`, `none` on an identity-valued product), `RistrettoIdentity`/`RistrettoBasePoint`, `ristrettoDecode`/`ristrettoEncode`, the group operators `+`/binary `-`/unary `-`/`==` (this codebase's first operators), `ristrettoScalarmultBase`/`ristrettoScalarmult`/`ristrettoScalarmultVartime`, `ristrettoFromUniformBytes`, `ristrettoStaticSecret`/`ristrettoStaticPair`/`toRistrettoStaticSecret`/`toRistrettoStaticSecretWide`/`ristrettoEphemeralSecret`/`ristrettoEphemeralPair`/`toRistrettoEncoded`/`toBytes`/`wipe`/`$`/`hash` (`ristretto.nim`'s own module doc comment and its list below have the full rationale; `ristrettoUnchecked` and `scalar.SecretScalar` are deliberately NOT exported). Consumers `import sello`; submodules are importable but carry no stability promise.

Modules under `src/sello/`, each built strictly on the one(s) below (with one standing exception: `private/ct.nim` is a universal leaf that secret-holding modules at any position reach into directly, regardless of list order):

1. **`field.nim`** — GF(2²⁵⁵−19) arithmetic. Radix 2²⁵·⁵, 10 `int32` limbs (`Fe` object). Direct ref10/orlp port (public domain). All the `fe*` primitives: mul, sq, invert, `fePow22523`, encode/decode, canonicity check (`feBytesCanonical`), constant-time `feCMove`/`feCSwap`, and `clampScalar` (shared by ed25519 and X25519 clamping — lives here so `x25519.nim` stays a `field.nim`-only consumer). Also `feFromLimbs` (RFC-003 slice 1: the one audited construction door for limb-built `Fe`s — `Fe.limbs` stays public for the arithmetic core's hot-path mutation, but every constant-from-raw-array site goes through this except the trivial 0/1 constants `FeZero`/`FeOne` (`field.nim`), which construct `Fe(limbs: [...])` directly rather than through the door — matching `feFromLimbs`'s own doc comment, which is precise about this rather than claiming blanket coverage) and vartime `feSqrtRatioVartime` (the RFC 8032 §5.1.3 sqrt-ratio dance — candidate root, sqrt(-1) retry, reject — extracted from `ed25519.pointDecode` so a future Ristretto decode can reuse it without importing the verify module; the sqrt(-1) constant moved here from `scalar.nim` with it, now unexported, since it's a field-only property with no curve equation baked in).
2. **`wire.nim`** — leaf module (round-2 findings 27/28, split from the combined `types.nim` by RFC-002 slice 2 item 5): nominal wire types `PublicKey`/`Signature` (`distinct array[32/64, byte]`, RFC-001 finding 9) plus their `toPublicKey`/`toSignature`/`toBytes`/`==`/`$`/`hash` borrows — no crypto logic of its own, and (unlike the old combined module) no `private/ct` import either, since these types hold no secret to wipe. Relocated out of `scalar.nim`, which was holding these purely so `ed25519.nim` and `signing.nim` had a shared downward import; that polluted `scalar.nim`'s group-ops mandate with wire-format/hygiene concerns its arithmetic never touches. `ed25519.nim` (verify) and `signing.nim` (sign) both depend on `wire.nim` directly now; `ed25519.nim` still re-exports the types so `import sello/ed25519` alone finds them (preserved compatibility).
   **`wipe.nim`** — the other half of the old `types.nim` split (RFC-002 slice 2 item 5): the generic secret wipe `wipe*(var array[32, byte])` (RFC-001 finding 11), delegating to `sello/private/ct` (a leaf itself). `types.nim`'s own doc comment had admitted the wire types and this wipe shared that module for import-graph position only, not a common purpose ("two leftover leaf concerns, one roof"); splitting gives each its own single-purpose roof.
   **`challenge.nim`** — the ed25519 challenge hash `challenge(R, A, msg)` (RFC 8032 §5.1.6 step 4 / §5.1.7 step 2), extracted out of `scalar.nim` by RFC-002 slice 2 item 1: it was the one thing in that file pulling in SHA-512. Imports `sello/scalar` (for `scReduce`) and `sello/private/sha512` (RFC-006: in-house SHA-512, swapped in for the former `nimcrypto/sha2` import in slice 3); consumed by `ed25519.nim` (verify) and `private/backend.nim` (sign) — one audited copy of the formula shared by both, so sign/verify can never silently drift apart.
   **`private/sha512.nim`** — in-house SHA-512 (RFC-006, FIPS 180-4), replacing the `nimcrypto` dependency this project resolved through 0.4.0; sello resolves zero dependencies in the core as of this module landing. A leaf module, `private/ct.nim`'s sibling in the layering: imports nothing but `private/ct` for its own secret wipes. Production face is three fixed-arity one-shot `func`s (`sha512(a)`/`sha512(a, b)`/`sha512(a, b, c)`, `openArray[byte] -> array[64, byte]`) — the only shapes any real call site needs (Nim cannot express `varargs[openArray[byte]]`) — each running `init`/`update`×N/`finish` on a stack-confined context and `ct.wipe`-ing it before returning; a streaming `Sha512Context`/`init`/`update`/`finish` register stays exported for the test estate only (CAVP incremental-split/boundary coverage, `test_ct.nim`'s whole-object wipe scan). The compression core wipes its own rolling 16-word message schedule and eight working variables via `private/ct`'s word-granular `wipe[N](var array[N, uint64])` overload (added alongside this module, RFC-006 slice 1b) after a redesign from a fully-materialized 80-word schedule to a rolling 16-word one cut the per-call wipe overhead from a measured ~50% back to the RFC's expected single digits (~8%, re-measured). Consumed by `challenge.nim` and `private/backend.nim`; under `private/` since it is not public API — sello is a 25519 library, not a hash toolkit (see RFC-006's Non-goals).
3. **`scalar.nim`** — Curve25519 group ops in extended Edwards coordinates (`GeP3`/`GeP2`/`GeP1P1`/`GeCached`). Point add/double, variable-base `scalarmultVartime` (verify-only, vartime — named with the suffix, RFC-001 finding 8, so it self-flags at every call site instead of relying on a doc comment to distinguish it from the CT signer code sharing this file), and fixed-base `geScalarmultBase` (signed radix-16 digits over a compile-time `GeCached` base table, CT `cmovCached` select — used by both keygen and signing, safe on secret scalars; a debug-only `assert` here checks its bit-255-clear precondition, wrapped in `when not defined(release)` so the dudect-measured build is untouched — plain `assert` alone does NOT get stripped by `-d:release` in this Nim 2.2.10 config, empirically verified, contrary to the RFC's stated assumption; see the assert's own comment). Also declares `SecretScalar` (round-3 finding A3: `distinct array[32, byte]`, no converter to/from a bare scalar array) — the type-level gate that makes "a secret scalar can never reach `scalarmultVartime`" a compile error rather than a naming convention; `geScalarmultBase` and `scMulAdd`'s two secret-scalar parameters accept only `SecretScalar`, `scalarmultVartime` accepts only `array[32, byte]`, and `private/backend.nim` is the one caller that constructs one (see that module and `SecretScalar`'s own doc comment for the full home/scope reasoning, including why `x25519.nim`'s ladder and `recodeScalarRadix16` deliberately stay untyped byte-level code below this boundary). `scReduce`/`scIsCanonical`/`scMulAdd`/`pointEncode` also live here (moved down from `ed25519.nim` so the signing backend never imports the verify-only module); the shared `challenge(R, A, msg)` hash that used to live alongside them moved out to `challenge.nim` (above) in RFC-002 slice 2, taking this file's only nimcrypto import with it — `scalar.nim` is now a pure field-plus-curve-math leaf with no nimcrypto dependency. Curve constants (`Ed25519D_Raw`, `Ed25519Gx/Gy_Raw`) live here too (`SqrtM1_Raw` moved to `field.nim` as `feSqrtRatioVartime`'s private constant — RFC-003 slice 1; it's a field property, not a curve one). `geSub` (dead ref10-port residue, zero call sites) was deleted in the same slice. Back to pure group ops as of round 2 — the wire types it used to hold moved to `wire.nim` (above).
4. **`ed25519.nim`** — RFC 8032 layer: `pointDecode` (strict §5.1.3: rejects y ≥ p and x=0-with-sign-bit) and `verify` (`openArray[byte]` and `string` overloads, taking the nominal `Signature`/`PublicKey` from `wire.nim`). Verify-only, never touches a secret, no backend dispatch — pure-Nim always, including under `-d:selloLibsodium`.
5. **`x25519.nim`** — RFC 7748 layer on `field.nim` only (no Edwards code): Montgomery ladder (branchless on the secret scalar, `private/ct.nim`-wiped after use), `x25519` (returns `none` on all-zero shared secret, i.e. small-order peer point) and `x25519Base`. Role-typed wrappers, one per X25519 role, not one type for all three (RFC-001 ledger #29, revisited on Corey's direction — supersedes finding 9's original one-`X25519Key` design), and the SECRET role is itself split in two (the X25519 static/ephemeral batch, closing the deferral this list used to record): `X25519StaticSecret` (a reusable private scalar; one-field object, not `distinct array`, for the same empirically-established reason `signing.Seed` isn't — see its doc comment — `=destroy`-wiped, deliberately copyable like `Seed`, every copy self-wipes independently), `X25519EphemeralSecret` (a SINGLE-USE private scalar, x25519-dalek's `EphemeralSecret` in this module's own vocabulary: move-only — `=copy {.error.}`, the `Keypair` pattern — constructed ONLY via `x25519EphemeralSecret()` (fresh from `std/sysrand`, no from-bytes route: freshness by construction), with NO `toBytes` either (unpersistable by design); `x25519Base(secret: X25519EphemeralSecret)` is a non-consuming plain-value borrow, `x25519(secret: sink X25519EphemeralSecret, peer)` CONSUMES it — `sink` plus the move-only `=copy` error together make reuse a compile error, fixture-verified (`tests/unit/fixtures/reject_ephemeral_reuse.nim`, `reject_ephemeral_copy.nim`, driven by subprocess `nim c` in `test_x25519.nim` — `compiles()`/`nim check` cannot see this error class, same reason as `Keypair`'s copy fixture) rather than a documented caller obligation), `X25519Public` (a public u-coordinate; plain `distinct array[32, byte]`, freely copyable, no destructor), and `X25519Shared` (a completed DH output; same shape as `X25519StaticSecret`, since it IS secret material). RFC 7748 does treat all three wire roles as the identical 32-byte format, and one type for all of them closed the cross-algorithm mixup (`verify(sig, msg, x25519Key)`) at zero ergonomics cost — but it also meant role confusion between secret and sendable X25519 material failed open, and gave no way to express "this secret must not outlive one exchange." Splitting the secret role further mirrors `Seed`/`PublicKey` on the ed25519 side for the sendable/secret boundary, and closes the single-use gap the same way `Keypair`'s move-only `=copy` closes accidental duplication. **Empirical Nim-ownership finding, load-bearing for the ephemeral design (verified via isolated scratch probes on Nim 2.2.10/ORC, not assumed):** the sink-argument "is this the last read" check is a simple per-symbol occurrence count over the whole scope, not an escape/alias analysis — ANY earlier reference to the same variable (even a bare field read or `addr`, confirmed directly), or the call merely sitting inside a `try`/`finally` (which `unittest.test` wraps every test body in), makes a later bare `x25519(secret, peer)` require a copy it cannot make; the caller must use `system.move` (`x25519(move(secret), peer)`, which needs `secret` declared `var`) whenever `x25519Base` (or anything else) touched the same variable first. A genuinely sole, un-annotated consuming call needs no `move()` — ordinary last-use inference already covers it (see `x25519.nim`'s doc comment on the `sink` overload for the full writeup, including the honest residual gap: `move()` is Nim's own explicit override of this analysis, so a caller who writes it at two separate consuming call sites for the same variable would compile — the natural, unadorned reuse pattern the negative fixtures actually cover remains correctly rejected). All types stay in `x25519.nim` rather than moving to `wire.nim`: they are RFC 7748's own types, with no consumer outside this module's own RFC 7748 layer, unlike `PublicKey`/`Signature`, which two separate upward modules needed to share. Also exports `toX25519StaticSecret`/`toX25519Public`/`toBytes`/`x25519StaticSecret()`/`x25519StaticPair()` (RFC-003 slice 1: bundled fresh-secret-plus-public constructor for the static role, mirroring `x25519EphemeralPair()`'s shape — a full `Keypair`-style invariant object was considered and declined since X25519 ops take only the secret)/`x25519EphemeralSecret()`/`x25519EphemeralPair()` and the `X25519StaticSecret`/`X25519EphemeralSecret`/`X25519Shared`-typed `wipe` overloads (RFC-001 finding 11) that give callers holding X25519 secret material outside a `Keypair`/`Seed` a supported route to `private/ct.wipe`; the generic `array[32, byte]` `wipe` overload lives in `wipe.nim` (round-2 finding 28, its own leaf as of RFC-002 slice 2), not here, since it isn't X25519-specific.
6. **`ristretto.nim`** — the ristretto255 prime-order group (RFC 9496, RFC-004), built on `field.nim` + `scalar.nim` only — a sibling of `x25519.nim` in the layering, below `ed25519.nim`/`signing.nim`, above the field/curve core; never imports the verify-only module, `challenge.nim`, or a backend, and stays nimcrypto-free (hash-to-group takes 64 caller-hashed bytes, per RFC 9496 §4.3.4 leaving the hash out of scope). Internally it IS the existing extended-Edwards arithmetic (`GeP3` add/double/scalarmult reused unchanged) wrapped in an encode/decode/equality/map layer that quotients away the cofactor-8 ambiguity a raw `GeP3` carries — every `RistrettoPoint` names one group element with exactly one canonical 32-byte encoding (`RistrettoEncoded`). **CT posture (load-bearing, mirrors the VERIFY/SIGN split's own care but cuts across it differently):** decode/encode/equality/the map are CT by construction (straight-line field arithmetic plus `feCMove`-based selects); the final accept/reject verdict (`ristrettoDecode`'s `none`, `==`'s result) is inherently caller-visible and carries no CT obligation of its own. This diverges from `ed25519.verify`'s "no CT requirement at all" posture because ristretto255 elements are routinely *derived from* secrets in the protocols this module serves (a Pedersen commitment before publication, an OPRF blinded element, a DH share) even though the encoding eventually goes on the wire. `RistrettoPoint`'s `==` is therefore CT (the one `==` in this codebase that is, diverging deliberately from `wire.nim`'s vartime register); `RistrettoEncoded`'s `==` stays the ordinary vartime byte-compare, an intentional split an operator cannot self-flag (no `Vartime` suffix on an operator) — see the module's own doc comment and README's Ristretto255 section for the encode-then-compare timing trap this creates. New CT field primitives back this (`field.nim`): `feSqrtRatioM1` (RFC 9496 §4.2's three-check `SQRT_RATIO_M1`; `ed25519.pointDecode` was REWRITTEN onto it and the old vartime `feSqrtRatioVartime` DELETED — two independently-maintained sqrt-ratio implementations in one codebase is exactly the drift mode `challenge.nim` exists to kill), `feEqualCT`/`feIsZeroCT`/`feBytesCanonicalCT`, `feAbs`, and a re-exported `FeSqrtM1`. Scalar multiplication ships in both registers behind the same `SecretScalar` type gate the rest of the codebase uses: `ristrettoScalarmultVartime` (bare `array[32, byte]` only, a secret scalar cannot reach it — a compile error, not a convention) and, on the secret-scalar side, `ristrettoScalarmultBase` (CT fixed-base, over the existing `geScalarmultBase`) plus `ristrettoScalarmult` (CT variable-base, over new `scalar.geScalarmultCT` — a uniform 256-doubling interleaved radix-16 ladder with a runtime 8-entry `GeCached` table, NOT a clone of `geScalarmultBase`'s odds/×16/evens shape, which only works for a table pre-scaled by 16^(2j); the operation that makes the group usable for OPRF evaluation, Pedersen commitments, and DH shares over an arbitrary point, R1-wipe-disciplined throughout). Two secret-scalar role types mirror X25519's static/ephemeral split: `RistrettoStaticSecret` (reusable — a Pedersen key, an OPRF server key; copyable, self-wiping, always a canonical residue mod L, `toRistrettoStaticSecret` REJECTS non-canonical import while `toRistrettoStaticSecretWide` totally reduces — named distinctly, not overloaded by array length, since reject-vs-reduce is a security-semantic difference) and `RistrettoEphemeralSecret` (single-use, move-only — an ElGamal/ECIES-style one-shot DH share: ephemeral k, `C1 = ristrettoScalarmultBase(k)` borrowed and sent, then `S = k·P` via the ONE consuming `ristrettoScalarmult(sink ..., ...)` call, k dead thereafter, RETURNING `RistrettoShared` — not `RistrettoPoint` — since `S` IS the shared secret itself (DH shared-secret hygiene fix, closing a gap where the actual DH output carried no wipe path: `RistrettoShared` is the `x25519.X25519Shared` shape, one-field object, `secretHooks`-wiped, `toBytes`); a CPace-style PAKE's two-mults-one-scalar shape does NOT fit this type by design and routes to `RistrettoStaticSecret` + `wipe` instead, documented as the honest boundary rather than a defect — that static-role `ristrettoScalarmult` overload deliberately still returns a plain `RistrettoPoint`, since ITS documented consumers (OPRF server, Pedersen) publish the result; a static-role DH caller instead follows an explicit encode-and-wipe/minimize-lifetime idiom documented on that overload). `RistrettoPoint` itself is freely copyable with deliberately NO `wipe` overload and NO `hash` overload for every OTHER scalarmult result: elements are PUBLIC-register values in every protocol this serves (the published commitment/blinded element is never itself the secret — the scalar that derived it is, and that scalar's role type owns the hygiene), and a hash must agree with `==`, which only the canonical encoding (`RistrettoEncoded`, which DOES have `hash`) guarantees across representations — key/dedupe on the encoding, never the point. **Non-goal, stated honestly rather than left implicit:** this module ships the GROUP, not a scalar-arithmetic API — a Schnorr response needs `scalar.scMulAdd` (exists, submodule-only, deliberately not facade-exported, since exporting it would drag the bare hygiene-free `scalar.SecretScalar` into the public surface); an OPRF CLIENT's unblind step needs mod-L scalar inversion, which exists NOWHERE in sello at any layer (`field.feInvert` is mod-p field inversion, unrelated) — so v1 serves commitment/DH/blinding-shaped protocols and an OPRF SERVER's evaluation step, not an OPRF client or a Schnorr prover. Facade-exported (`src/sello.nim`) as an ENUMERATED symbol list, matching that file's own precedent; `ristrettoUnchecked` (the module's one `feFromLimbs`-style raw-`GeP3` construction door, used by this module's own constructors/group ops and `test_ristretto.nim`'s white-box oracles) and `scalar.SecretScalar` are deliberately NOT among the exports.
7. **`signing.nim`** — `Seed`/`Keypair` types (fields private, move-only `Keypair`, `=destroy` wipes), the `keypair(seed)`/`keypair()` constructors, `keypair(seed, expectedPublic): Option[Keypair]` (janus consumer finding 2 — the load-time gate for persisted keys whose storage carries both halves, e.g. OpenSSH's/libsodium's `seed(32) ‖ publicKey(32)` layout: re-derives the public key and returns `none` on mismatch, because sello's re-derivation otherwise makes a corrupted stored key fail OPEN — it signs successfully under a public key the caller never presented; `Keypair` being move-only, the extraction idiom is `move(loaded.get())` via the `var Option` `get` overload), `sign`, and the `when defined(selloLibsodium)` backend dispatch (`private/backend_sodium` vs. `private/backend`, bound to one local name so every call site is backend-agnostic; that backend's `SodiumInitError` is re-exported here and through the facade under the flag, since it now appears in declared `{.raises.}` effects). Depends on `wire.nim` directly for `PublicKey`/`Signature` (not `ed25519.nim` — signing has no business importing the verify-only module; not `scalar.nim` either, since round 2 moved those types out of it). The facade re-exports from here with no conditional logic of its own.
8. **`private/backend.nim`** — the pure-Nim secret-math backend: seed-level `derivePublic`/`signDetached`, no `Keypair` knowledge. Builds on `field.nim` + `scalar.nim` + `challenge.nim` + `private/sha512.nim` (in-house SHA-512, RFC-006 slice 3 — `nimcrypto` is gone from this file and from the dependency tree entirely) only. Under `private/` because its exports bypass every `Keypair` guarantee (no invariant, no auto-wipe) — application code should use `sello.keypair`/`sello.sign`, never this module directly. `signDetached` carries a debug-only `assert` (RFC-002 slice 2) re-deriving and checking the caller-supplied public key against the secret scalar — expensive on purpose, wrapped in `when not defined(release)` (not a bare `assert`) so it is entirely absent from the dudect-measured/shipped release build.
9. **`private/backend_sodium.nim`** — the libsodium FFI adapter (only compiled under `-d:selloLibsodium`), mirroring `backend.nim`'s exact seed-level contract via `crypto_sign_seed_keypair`/`crypto_sign_detached`; atomic `sodium_init` once-guard (`std/atomics`, not a plain check-then-set flag). Also carries four ristretto255 oracle wrappers (RFC-004 slice 8c: `sodiumRistrettoIsValidPoint`/`sodiumRistrettoFromHash`/`sodiumRistrettoScalarmult`/`sodiumRistrettoScalarmultBase`) plus `sodiumLibraryVersion` — differential-test oracles ONLY, never wired into `signing.nim`'s dispatch (Ristretto has no backend-dispatch story of its own; see `ristretto.nim`'s own non-dispatch design and RFC-004's Non-goals), consumed exclusively by `test_libsodium_interop.nim` behind a runtime libsodium >= 1.0.18 version assert (the first version-sensitive API this file wraps).
10. **`private/ct.nim`** — the one audited secret-wipe primitive (`wipe[T]`: volatile per-byte stores + `asm volatile("" ::: "memory")` barrier, `{.noinline.}`), called from `backend.nim`, `x25519.nim`, `wipe.nim`, `ristretto.nim`, `private/sha512.nim`, and (as of round-3 finding A5) `private/secret_hooks.nim` — a small `{.dirty.}`-template pair (`secretHooks`/`secretHooksMoveOnly`) that emits the `zeroize<Type>`/`=destroy`/optional `=copy {.error.}` boilerplate once, instantiated by `signing.nim` (`Seed`), `x25519.nim` (`X25519StaticSecret`/`X25519EphemeralSecret`/`X25519Shared`), and `ristretto.nim` (`RistrettoStaticSecret`/`RistrettoEphemeralSecret`/`RistrettoShared`) in place of hand-copied versions of the same shape. `Keypair`'s own `=copy {.error.}` stays hand-written (no `bytes` field of its own to wipe — see the template module's doc comment). As of RFC-006 slice 1b it also exports a word-granular sibling `wipe[N](var array[N, uint64])` overload — same volatile-store-plus-barrier shape, per-`uint64` instead of per-byte — that `sha512.compress`'s message-schedule/working-variable wipes route to automatically via overload resolution, cutting that per-block wipe cost roughly 30x (704 byte-stores to 24 word-stores) as part of the redesign that brought sha512's wipe overhead down from ~50% to ~8%.

`tests/ct/` (`dudect.nim` + `ct_main.nim`) is the dudect-style timing harness, run via `scripts/ct.sh` — see below.

## Building & testing

**milpa** (Corey's Nim dependency resolver, `~/.local/bin/milpa`) is the authoritative resolver for development — not nimble. It reads `milpa.kdl`, clones deps into `_deps/` (content-addressed under `~/.cache/milpa`, gitignored), and writes `milpa.lock` (commit SHA + dag-sha256 content identity + provenance per dep). As of RFC-006 (in-house SHA-512 retired the `nimcrypto` dependency), a plain `milpa fetch` resolves ZERO dependencies — `milpa.lock` records only `proptest` (plus its own transitive `nim-z3`/`softlink`), and only once fetched with `--features proptest` (see below; NOTICE has the current provenance record). Run `milpa fetch` once after cloning (and again after editing `milpa.kdl`) to populate `_deps/` and emit `nim.cfg`.

There is **no host Nim toolchain** in this environment; all builds happen in the base toolchain image. `scripts/test.sh`, `scripts/test-libsodium.sh`, and `scripts/ct.sh` (replacing the old nimble tasks) wrap the exact podman invocation, mounting the project plus the milpa CAS at both its canonical path and its host-absolute path (so milpa's absolute dep symlinks under `_deps/` resolve in-container).

`Containerfile.amox` is **amoxtli's sandbox image**, unrelated to sello (its package list — rust/go/node/openssl — belongs to a different project entirely); do not confuse the two or bolt sello-specific packages onto it. sello owns a `Containerfile` of its own (`FROM ghcr.io/coreyleavitt/nim@sha256:...` — digest-pinned, not the `2.2.10` tag, per the paragraph below — plus `libsodium-devel`, `z3-devel`, and, as of RFC-005 slice 7's "Image consolidation," the full package set the *whole* RFC needs: `gcc-32bit`/`glibc-devel-32bit`/`libstdc++6-32bit` for slice 10's `--cpu:i386`/`-m32` job, `valgrind` for slice 19, `lcov` for slice 17, `cross-s390x-gcc16` + `qemu-linux-user` for slice 25's nightly cross-compile job — `binutils` and `clang` are NOT added, since both are already present in the base image, verified empirically rather than assumed; see the Containerfile's own header comment for the full enumeration, including the one substitution finding (`qemu-user-static`'s Debian/Ubuntu name doesn't exist on this zypper base — the package is `qemu-linux-user`)), built as the `sello-dev` image and used by `scripts/test-libsodium.sh` (libsodium adapter matrix) and `scripts/bmc.sh` (Z3-backed symex proof, RFC-001 finding 22) today, plus later RFC-005 Phase 1-3 job wiring as it lands — one image, one Containerfile, covering every matrix, rather than maintaining near-duplicate layers (the RFC's own two-image lean-core/heavy-gates split stays pre-authorized if a future pull-cost measurement ever breaks budget). `scripts/test.sh`, `scripts/ct.sh`, and `scripts/fuzz.sh` need neither this image nor network access.

**sello-dev: publish-by-digest and the (Containerfile-hash, digest) drift pin (RFC-005 slice 7).** `scripts/test-libsodium.sh` and `scripts/bmc.sh` no longer build `sello-dev` locally if missing — both pull `ghcr.io/coreyleavitt/sello-dev` BY DIGEST via `scripts/lib/sello-dev-image.sh` (`resolve_sello_dev_image`), reading the pinned reference from `scripts/lib/image-pins.txt`'s `sello-dev` line. **Base-image `FROM` pin, and a live mutable-tag finding (RFC-005 slice 7).** The Containerfile's `FROM` is now digest-pinned (`ghcr.io/coreyleavitt/nim@sha256:...`, matching `scripts/lib/image-pins.txt`'s base-image section), not the `2.2.10` tag it used before this slice. The manifest-LIST digest recorded in the pin file stayed stable and correct throughout, confirming digest-pinning is what actually protects a build from this class of drift.

**proptest** (property-based testing, RFC-001 finding 10) is an *optional* milpa dep: `milpa.kdl` declares it `optional=#true`, which milpa desugars into an auto-flag named `proptest` (default off) gating the dep — so `milpa fetch` alone (what a downstream consumer of sello runs) never fetches proptest or its own transitive deps (`nim-z3`, `softlink`; proptest's manifest depends on `nim-z3` unconditionally). To build/run the property tests, fetch it explicitly once: `milpa fetch --features proptest` (root-level `--features` flag, RFC #23 §3.4) — this populates `_deps/proptest`, `_deps/z3`, `_deps/softlink` and adds their `--path` lines to `nim.cfg`. `import proptest` compiles and links fine in the base image with no z3 shared library installed: the only proptest module that imports `z3` is `proptest/symex`, which the top-level `proptest` module never imports (confirmed empirically, not merely by reading the source). Re-running a plain `milpa fetch` afterwards prunes proptest back out (activation is recomputed from the manifest + requested features every fetch, not preserved from the lock) — this also means `milpa.lock`'s proptest/z3/softlink entries come and go with which fetch you last ran; that's expected, not a hygiene problem.

**RFC-005 slice 2 re-pin:** `milpa.kdl`'s `proptest` dep is pinned by commit SHA (`ec7a405c354e79c30717b0692ad548bc8bee7414`), not `ref="main"` — an unpinned branch ref left the code that executes in required CI jobs (the property suites) with no integrity check (milpa 0.0.1's `verify` has no `--features` flag, so it never covered this optional dep either). The `deps` block's git URL points at the **canonical** repo, `nelli` (github.com/coreyleavitt/proptest was renamed 2026-08-13; the redirect works today, but a future rename-reuse of the freed `proptest` name could otherwise silently retarget this dependency) — the local dep alias stays `"proptest"` (arbitrary; it is `import proptest` that must keep resolving, and Nim import resolution is driven by the fetched package's own `src/proptest.nim`, not this alias). The pinned commit is deliberately NOT `nelli`'s current main HEAD: commit `785307c` ("refactor: rename package proptest -> nelli", 2026-08-13) renamed the Nim source tree itself (`src/proptest.nim` -> `src/nelli.nim`, the whole umbrella-module identity), not just the GitHub repo, and every `test_properties_*.nim` file in this project does `import proptest` — following main past that commit would break every one of those imports and demands a project-wide `import proptest` -> `import nelli` sweep, which is its own deliberate migration, not a CI-integrity slice's job. `ec7a405c354e79c30717b0692ad548bc8bee7414` is the newest commit before the rename. `nim-z3` is pinned the same way via a top-level `overrides { pkg "z3" ... }` block (nelli's own manifest still pins z3 at `ref="main"`, the same mutable-branch hole one level down the transitive graph — z3 is resolved/fetched by the property job but never compiled, since only `proptest/symex` imports it); `softlink` is left unoverridden since nim-z3's own manifest already pins it by version tag, not a branch. The CI property job (`scripts/ci-property.sh`) asserts the fetch matches this pin via `milpa fetch --features proptest --locked` (milpa's own built-in "resolve then assert against the committed lockfile, identity + provenance" check — RFC-005 Part B's "dag-sha256 identity where milpa exposes it").

`milpa fetch` emits `nim.cfg` **wholesale** (`--path:"src"` + one `--path` per resolved dep) — it owns that file entirely and rewrites it on every fetch, so nothing else may live there. The project-standing `--mm:orc`/`--outdir:"build"` flags instead live in root `config.nims` (`switch("mm","orc")`, `switch("outdir","build")`), a file milpa never touches; Nim reads both `nim.cfg` and `config.nims` for every invocation, so the two compose without conflict. `build/` is gitignored — never commit binaries. `nim.cfg` and `_deps/` are also gitignored (regenerated by `milpa fetch`); `milpa.kdl` and `milpa.lock` ARE committed.

### CI (RFC-005: validation infrastructure)

Nightlies releases are tagged by build date against a branch, not by exact patch release, so most tags sit a few commits ahead of any given `vX.Y.Z` tag — this project verified (2026-08-24, `gh api repos/nim-lang/Nim/tags`) that the `v2.2.10` git tag itself resolves to commit `bfeb3146d1638b39f69007a4ae5a23e23ae4e5ef`, and that nightlies published a release built from that EXACT commit (`2026-04-24-version-2-2-bfeb3146d1638b39f69007a4ae5a23e23ae4e5ef`) — so the pinned binary (`nim-2.2.10-linux_arm64.tar.xz`, SHA-256 `cd86a6e2bcbf029c4870aa51df5c0169345dbf9959889112fd15d403c13ae33a`) is built from the identical source commit as the `ghcr.io/coreyleavitt/nim:2.2.10` container image tag every other job runs inside, not merely "a nearby nightly." **Mechanism decision (prebuilt binary over choosenim or a from-source build):** all three options were investigated; choosenim builds from source on unsupported arches (slow, and needs its own pin story on top) and a direct `build_all.sh` source build from the `v2.2.10` tag (~5–15 minutes) would need `actions/cache` to stay inside budget — the prebuilt-binary route needs neither: a statically-linked ~16 MiB `.tar.xz` downloads and extracts in low single-digit seconds (confirmed empirically), so **no `actions/cache` is used for the toolchain install** — a saving this small doesn't meet the bar RFC-005 Part B's wall-clock-budget paragraph had in mind when it authorized caching the toolchain "if building from source," and skipping it entirely sidesteps opening a second authorized cache scope beyond Part B's existing one (today: "the Actions cache is used only for the fuzz working corpus, keyed so non-main branches cannot seed main-consumed entries"). Every download is SHA-256 verified before extraction; a mismatch is a loud, non-retried failure (treated as a supply-chain event, same posture as `scripts/policy-lint.sh`'s actionlint pin). **Platform-identity canary:** `scripts/ci-nim-setup.sh --expect-arch aarch64` asserts `uname -m` before installing anything — the arch-canary half of RFC-005 Part B's matrix-leg rule, proving the runner is genuinely arm64 rather than a mislabeled/reverted runner image; `scripts/test.sh`'s existing `toolchain-canary.sh` call still runs unconditionally underneath (gcc, unchanged), so this leg also proves C-compiler identity for free, same as every other leg. **PATH mechanism (deliberately not `$GITHUB_PATH`):** `ci-nim-setup.sh` installs to `$HOME/.sello-nim/nim-<version>-<platform-key>/` and updates a stable `$HOME/.sello-nim/current` symlink; `scripts/test.sh` itself checks for `$HOME/.sello-nim/current/bin/nim` at its own top and prepends it to `PATH` when present — a plain on-disk convention that works identically whether `ci-nim-setup.sh` ran as an earlier, separate workflow step (where a `$GITHUB_PATH` write only takes effect starting the NEXT step) or is chained via `&&` on one command line (`scripts/lib/gates.txt`'s form for these two gates — a subprocess's own `export PATH` would not propagate to the parent shell there either), and needs no GitHub-Actions-specific plumbing at all, so it works unchanged on a real arm64 host too. Idempotent (a marker file records the exact platform/release/asset/checksum tuple; a matching marker skips re-download). Both `unit-linux-arm64-gcc`'s and `property-linux-arm64-gcc`'s `scripts/lib/gates.txt` entries hardcode `SELLO_IN_CONTAINER=1` (`scripts/ci-nim-setup.sh --expect-arch aarch64 && SELLO_IN_CONTAINER=1 scripts/test.sh` / `... scripts/ci-property.sh`) rather than relying on each script's own dual-mode host branch, since there is no podman wrapping to skip in the first place on this leg — "in-container mode" is simply the only mode it ever runs in, locally or in CI; `scripts/merge-gate.sh --help` and its own header comment document this leg as a host-arch-dependent residual within "the Linux set" (fails loud via the arch canary on a non-aarch64 host, same category macOS/Windows will join in slices 12–13). `scripts/ci-property.sh` needed no changes: its milpa-venv install (python3 + pip, no compiled wheels) is architecture-independent and its `--cc`-forwarding shape already composed cleanly.

Build: x86_64, POSIX threading, SEH exception handling, UCRT runtime (`mingw-w64ucrt`) — the modern recommended combination; UCRT ships in-box on every supported Windows version as `ucrtbase.dll`, so no extra runtime install is needed. GCC 16.2.0. **`scripts/ci-nim-setup.sh --with-mingw`** (that script's own header has the full mechanism) installs this pin onto its own dedicated path, `$HOME/.sello-nim-mingw/current/bin` — a namespace deliberately separate from the Nim install's `$HOME/.sello-nim/current` — which `scripts/test.sh` now also checks and prepends to `PATH` (a small, unconditional, harmless-elsewhere addition mirroring the existing Nim-pin PATH convention exactly). **Two-part identity canary, the DoD's own load-bearing addition:** Git Bash's `uname -m` on 64-bit Windows reports `x86_64` — the SAME string a plain Linux amd64 host reports for the identical value, unlike the aarch64-vs-arm64 Linux/Darwin split every earlier residual leg could rely on — so `--expect-arch x86_64` alone cannot tell this runner apart from an ordinary Linux workstation. `scripts/ci-nim-setup.sh` therefore grew a SECOND, independent canary, `--expect-os <case-glob>` (this leg passes `'MINGW64_NT*|MSYS*'`), asserted against the RAW `uname -s` value (before it gets folded down to a stable `windows` platform-key for the pin-table lookup — Git Bash's `uname -s` embeds the Windows kernel build number, e.g. `MINGW64_NT-10.0-20348`, which would otherwise force a new pin-table row every time GitHub bumps the runner OS build even though nothing about the pinned Nim binary changed; the OS canary checks the raw, unfolded string directly, so that per-build variability doesn't need its own pin row at all). Plus a toolchain-VERSION canary specific to `--with-mingw`: after extraction, the installed `gcc --version` output is asserted to contain the exact version string `mingw-pin.txt` records (`16.2.0`) — proving the PINNED gcc landed, not merely a gcc-named binary from wherever extraction happened to put one (this slice's own DoD: "toolchain canary confirming the PINNED gcc"). `scripts/test.sh`'s own `scripts/lib/toolchain-canary.sh` call still runs unconditionally underneath (gcc, the default `--cc`), proving Nim genuinely invoked it, for free, exactly like every other leg. **`--expect-proptest-skip`:** identical mechanism and rationale to the macOS leg's own use of this flag, immediately above. **Portability, verified against the real zip rather than assumed:** the archive's own top-level directory is `nim-2.2.10` (same convention as every `.tar.xz` row, so the existing `mv "$extract_tmp"/nim-*/* ...` line needed no change) — the ONLY extraction-mechanism change this slice needed was branching on the asset's own extension (`.zip` vs `.tar.xz`), preferring `unzip` and falling back to `tar -xf` (Windows' own in-box bsdtar extracts `.zip` natively). `scripts/merge-gate.sh --help` and its own header comment document this leg as the third hosted-only residual, rejecting a non-Windows host at the OS canary specifically (one step earlier than the arm64/macOS legs' arch-canary rejection, since arch alone would otherwise pass on an ordinary Linux amd64 workstation).

**Nightly fuzz continuity (RFC-005 slice 24, A5 — taken deliberately out of order: slices 10/14/15/17/19–23/25 remain blocked on the same Corey-owned ghcr `write:packages` credential for the `sello-dev` image, and slice 27 is Corey-physical; this slice needed only the always-available base image plus the already-public proptest dependency, so it was pulled forward ahead of 25, the identical judgment call slices 11/16/18 already made).** `.github/workflows/nightly.yml` is a SEPARATE, non-required workflow (`schedule:` cron at `17 3 * * *` UTC plus `workflow_dispatch:` with inputs for on-demand budget/staleness-threshold/cold-start/crank/force-failure/timeout-demo overrides — the last three added by RFC-005 slice 26, see its own paragraph below) — not in `scripts/lib/gates.txt`, not a `merge-gate.yml` job, badged in README.md's Validation section as of RFC-005 slice 26 (`?branch=main`, matching the `merge-gate` badge's own pin). `gates-manifest-sync`/`ruleset-sync` both scan only `merge-gate.yml` by design (verified unaffected before this slice landed); `policy-lint` DOES scan every workflow file, and `nightly.yml` passes its four content assertions the same as the other two. Periodically (a maintainer's judgment call — e.g. after a nightly run's coverage-edge count jumps notably, or before a release), download a run's `fuzz-corpus-snapshot-<run_id>` artifact (or read a live `build/fuzz-corpus/*.bin` after a local `SELLO_FUZZ_CORPUS_DIR=build/fuzz-corpus scripts/fuzz.sh` run), inspect its entries (the `.bin` format is proptest's own `serialize.toBytes`/`fromBytes` choice-IR encoding — decode via a short scratch Nim snippet importing `proptest/db`+`proptest/serialize`, or replay a `.choices.bin` crash artifact the same way), and — for any entry judged genuinely interesting (new structure, not just a random near-duplicate of an existing seed) — hand-transcribe its concrete byte values into a new `array[N, byte]` constant appended to the relevant `*Seeds()` proc, exactly like every existing RFC-vector seed already there. This is a deliberate human act, never machine-committed (this project's own mutation-catalog precedent for "curated, not auto-regenerated" — see the Conventions/A3 register elsewhere in this file), and is never automated further than "the maintainer runs a decode snippet and edits a `.nim` file by hand."

**Nightly canaries + notifications (RFC-005 slice 26, Nightly part 3 — taken deliberately out of order: slice 25 (s390x, A4) and this slice's own A9 memcheck sub-item both remain blocked on the same Corey-owned ghcr `write:packages` credential blocking slices 10/14/15/17/19–23; slice 26's OTHER deliverables — cranked properties, notification wiring, the toolchain canary — need only the always-available base image, so they were pulled forward exactly as slice 24's own control-loop note anticipated).** Three deliverables landed in `.github/workflows/nightly.yml` (badged, see README.md); a fourth is its own separate workflow.
- **Pinned-issue notifications.** `scripts/lib/notify-failure.sh` is the one shared primitive both `nightly.yml`'s and `toolchain-canary.yml`'s own `notify` jobs call (RFC-005 Part B's build-path invariant, extended to the notification path): search for an OPEN issue carrying a marker label, comment on it if found (one issue reused across repeat failures, never issue spam), or create-and-pin one if not (pin via the GraphQL `pinIssue` mutation — REST has no issue-pin endpoint at all). `scripts/gates-manifest-check.sh` (CI check name `gates-manifest-sync`) is the workflow-vs-manifest drift check: asserts `.github/workflows/merge-gate.yml`'s job name set equals `scripts/lib/gates.txt`'s check-name set, in both directions. The workflow is hand-written YAML (jobs are heterogeneous; generating YAML would mean building a templater with no customer), so this is a light `awk` scan, not a real parser — kept honest by cross-checking its own two extractions (every job KEY vs. every job's own `name:` field VALUE) against each other before trusting either, and failing loud with both sets printed on any count or set mismatch (a "parse surprise," e.g. a job missing its `name:` field) rather than silently comparing a wrong set against the manifest. Self-referential by design: this check's own CI job must appear in both the workflow and the manifest, or it fails on itself. Needs no container (pure text scan) — runs on a plain `ubuntu-latest` runner (see `.github/workflows/merge-gate.yml`'s own job comment for the container-vs-plain-runner rationale), still exactly one `scripts/` invocation. As of RFC-005 slice 4 the two-independent-extractions awk scan itself lives in `scripts/lib/workflow-job-names.sh`'s `extract_workflow_job_names()` (factored out so `scripts/ruleset-sync-check.sh` can reuse the identical extraction — see below — instead of a second hand-typed copy); `gates-manifest-check.sh` sources it rather than carrying its own inline awk.

**Rulesets + branch model (RFC-005 slice 4).** `.github/rulesets/main.json`, `evidence.json`, `tags.json` are the committed, reviewed ruleset bodies GitHub's ruleset engine enforces once applied (`POST`/`PUT /repos/{owner}/{repo}/rulesets` schema) — one file per ruleset. `main`: `deletion` + `non_fast_forward` blocked, plus a `required_status_checks` rule whose `required_status_checks` array is committed EMPTY (`[]`) by design and never read literally — both `scripts/ruleset-apply.sh` and `scripts/ruleset-sync-check.sh` splice the real array in from `scripts/lib/gates.txt`'s check-name column at use time (via the shared `scripts/lib/ruleset-canon.jq`'s `set_required_checks($checks)`), so two independently hand-maintained copies of that array — one drift-prone way this could otherwise go wrong — simply cannot exist. `evidence`: `deletion` + `non_fast_forward` blocked on `refs/heads/evidence` (the orphan evidence branch does not exist yet as of this slice — verified live that a ruleset targeting a nonexistent branch applies and reads back cleanly; ruleset conditions are pattern-based, not existence-checked). `tags`: `update` + `deletion` blocked on `~ALL`. Bypass list empty on all three (round-1 correction, RFC-005 Part B: a listed admin silently bypasses required checks on ordinary push). Empirical API finding, load-bearing for the committed JSON shape (verified live against disposable probe rulesets before these files were written): a rule whose `parameters` equals that rule type's default/empty shape (`deletion`, `non_fast_forward`, `update` with its one boolean left at its `false` default) is echoed back by GitHub with NO `parameters` key at all, not `{}` — the committed files omit it to match what a live `GET` actually returns, and `ruleset-canon.jq`'s `normalize` strips an empty/absent one defensively regardless, in case a future rule addition reintroduces one.

`scripts/ruleset-apply.sh` (maintainer-run ONLY, never a CI job — needs an admin-scoped `gh` session, which no CI job carries) reads `.github/rulesets/*.json`, splices the generated required-check array into `main.json`'s placeholder, and for each file either `POST`s (no live ruleset of that name exists) or `PUT`s (one does) to converge live state to committed state. **`PUT`, not `PATCH`** — verified live against a disposable probe ruleset before this script was written: `PATCH .../rulesets/{id}` returns a bare 404 against this endpoint; `PUT` with the full body succeeds. Idempotent: running it twice with no committed-file change makes the identical `PUT`/`POST` calls but changes nothing live. **DEFAULT MODE IS DRY RUN** — prints the planned CREATE/UPDATE per ruleset and a normalized diff for updates, but performs no mutation; `--apply` is required to mutate for real. This safety valve goes beyond the RFC's own text but matches the codebase's standing caution culture (`baseline_update`'s CI guard, the release gate's stale-accept input): applying `main` for the first time is the exact moment direct pushes to `main` stop working.

`scripts/ruleset-sync-check.sh` (CI check `ruleset-sync`) asserts the FULL canonicalized live ruleset state equals committed — names, bypass list, enforcement flags, all rulesets — not a names-only comparison (round-2 finding: names-only "left the empty bypass list and force-push flags unenforced after day 1, silently regressing round-1 finding 3"). Three legs: (1) `gates.txt` vs. the workflow's own job names, via the shared `extract_workflow_job_names()` above — the same comparison `gates-manifest-sync` runs, re-asserted here because the RFC's own Rulesets paragraph scopes it into `ruleset-sync`'s own job, not solely delegated to the sibling check; (2) the live `main` ruleset's required-check names vs. `gates.txt`, waiver-adjusted (below), with its own specific, readable diagnostic; (3) the generic full-canonical diff, every `.github/rulesets/*.json` file against its live counterpart by name (`.github/rulesets/unavailable/` is a subdirectory, excluded by the top-level-only `*.json` glob both this script and `ruleset-apply.sh` use). Live ruleset reads work ANONYMOUSLY on this public repo — verified empirically (bare `curl`, no `Authorization` header, against both the list and single-ruleset `GET` endpoints, before this script was written) — so the script uses plain `curl` + `jq` with no `gh` CLI dependency at all, and adds a bearer token only when `GITHUB_TOKEN`/`GH_TOKEN` is set in the environment, purely for the 5000/hr-vs-60/hr rate-limit headroom on a check that runs on every push with no path filter; the CI job passes `GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}` via `env:` for exactly this. **Operational finding, recorded rather than worked around:** GitHub's ruleset list/detail endpoints show a brief (single-digit-seconds) propagation lag after a live `POST`/`PUT`/`DELETE` — a `ruleset-sync` run, or manual verification, immediately after a live edit can observe stale state. Wait a few seconds between any live `gh api` ruleset mutation and the next check run or push during a live-edit demo (discovered during this slice's own local verification, not anticipated by the RFC text).

**Waiver mechanism** (`scripts/lib/waivers.txt`, parsed by `scripts/lib/waivers.sh`): the emergency hatch for an infra outage that has taken a required check's LIVE-ruleset entry down, never for a genuinely red gate — closes the deadlock RFC-005 Part B names by its own example (dropping a flaky required check from the live ruleset to unblock a push would otherwise turn `ruleset-sync` itself red, blocking the very push the hatch exists to unblock). Three whitespace-separated columns, `check-name expiry reason` (reason runs to end of line, same convention as `gates.txt`'s own column 2). `expiry` is EITHER an ISO date (`YYYY-MM-DD`, expires inclusive — at or past that UTC calendar date) OR a full 40-character git commit SHA (expires once that SHA is an ancestor of the SHA being checked, via `git merge-base --is-ancestor` — `ruleset-sync`'s own checkout step uses `fetch-depth: 0`, full history rather than the default shallow clone, specifically so this works reliably against this repo's own small history). A SHA-form expiry this checkout cannot verify at all (commit not fetched, typo) is treated FAIL-SAFE ACTIVE with a loud caveat printed, never silently treated as expired. A live-missing check covered by an ACTIVE (non-expired) waiver is excluded from the comparison's "expected" set (so `ruleset-sync` passes for it) but the waiver — name, expiry, reason — is logged loudly on every run, never silent. An EXPIRED waiver does NOT excuse the gap: `ruleset-sync` fails loudly, naming the expired waiver specifically, in addition to the generic missing-check diagnostic. Deliberately a SEPARATE file from `gates.txt`, not a column extension: a waiver is an exceptional, time-boxed, reviewed statement about the LIVE ruleset's temporary departure from what's committed, not a property of the gate itself (see the file's own header comment for the full rationale, including why a `git log -p` on this one file surfaces the repo's entire outage history).

`scripts/policy-lint.sh` (CI check `policy-lint`) runs actionlint over every `.github/workflows/*.yml` plus five assertions of its own (RFC-005 Part B): every `uses:` pinned by a full 40-character commit SHA, no `continue-on-error: true` anywhere, a top-level `permissions:` block present, every `container:` image digest matching `scripts/lib/image-pins.txt`'s base-image section, and (RFC-005 slice 7) the root `Containerfile`'s content hash matching the hash recorded on `image-pins.txt`'s `sello-dev` line — the sello-dev (Containerfile-hash, digest) drift check; see that file's own header comment and CLAUDE.md's sello-dev paragraph above for the full mechanics and repin ritual. actionlint is not preinstalled on `ubuntu-latest` (unlike shellcheck) and this check must stay host-runnable (the `gates.txt` plain-invocation convention), so the script downloads the pinned-version release binary itself and verifies it against a SHA-256 checksum recorded in the script's own header (checked against the upstream release's own published checksums.txt before being pinned, and independently re-verified via a fresh download before the script was committed) rather than depending on a GitHub Marketplace action — mirroring `scripts/lib/milpa-install.sh`'s own "fetch/verify a pinned tool inside the script" precedent instead of adding another SHA-pinned Marketplace action for one tool. Cached under `build/policy-lint/` (gitignored) so repeat local/host runs skip the download; CI's container is ephemeral per job and always pays the one-time fetch+verify. Supported host: linux/amd64 only, matching this repo's existing "the linux set only" scope elsewhere (`scripts/merge-gate.sh`'s own help text).

**Push ruleset: unavailable on this repo, residual recorded honestly (RFC-005 slice 4).** The RFC anticipated a push ruleset restricting `.github/workflows/**`, `.github/rulesets/**`, and `scripts/lib/gates.txt` might be Enterprise-only or unavailable on a personal public repo. Verified live against two independent `422`s from disposable probe rulesets (each created with `enforcement: "disabled"`, confirmed to fail for the stated reason, then deleted): (1) `target: "push"` itself — `"Source public repos cannot have push rules"` / `"Source only org-owned repos can have push rules"` — push-target rulesets require an ORG-OWNED repository regardless of visibility; `coreyleavitt/sello` is a personal-account repo (`owner.type == "User"`). (2) the `file_path_restriction` rule type, tested independently against a `target: "branch"` ruleset to isolate the question from (1) — `"Invalid rule 'file_path_restriction': "` — plan-gated independent of target (GitHub's own docs bundle file-path/extension/size rules under Enterprise-only "metadata restrictions"). The intended design is preserved, inert, at `.github/rulesets/unavailable/push-workflow-and-policy-paths.json` — a subdirectory both `ruleset-apply.sh` and `ruleset-sync-check.sh` deliberately exclude via their top-level-only `*.json` glob, with the empirical findings recorded in the file's own JSON fields — matching this codebase's `-d:selloBmcFullUnroll` precedent for a preserved-but-superseded artifact rather than silently dropping the intent. The compensating control is `scripts/policy-lint.sh` above, exactly as RFC-005 Part B's own text names it ("plus the policy-lint check above for content drift below that threshold"): content inspection on every push, in lieu of a push-time path-restriction gate this repo's plan/ownership tier does not offer. Revisit if the repo ever migrates to an org-owned account (a trade-off already declined once, for a different reason — true workflow-scoping — in the RFC's timing-tier paragraph) or GitHub extends these features to personal-account public repos; neither is scheduled.

**Branch model, live as of RFC-005 slice 4.** Once `scripts/ruleset-apply.sh --apply` has run, `main`'s `required_status_checks` rule blocks any push whose exact SHA lacks passing check-runs for every `scripts/lib/gates.txt` name — a freshly authored commit has none, so **direct pushes to `main` are rejected from this point forward, including doc-only and fix commits.** The merge flow henceforth: land work on an `rfc-*` branch (the only fast-forward-eligible pattern, matching the RFC's own heavy-gate placement text elsewhere), let CI green the branch head, then `git push origin <branch>:main` fast-forwards `main` to a SHA whose checks already passed — the ruleset engine accepts branch-run check-runs reported against the arriving SHA (verified live, this slice's own DoD). A locally created merge commit is a NEW SHA with no check-runs of its own and gets rejected — merges are fast-forward only, by policy (the `non_fast_forward` rule already committed is sufficient; no separate `required_linear_history` rule is needed). Scratch/demo branches are deleted after use, both locally and on `origin` (`gh api repos/.../branches/<name>` → 404 confirms).

**Check-rename two-step**, reaffirmed now that the ruleset exists (RFC-005 Part B): a required check name is a stable public interface (a ruleset required-check key, a `gates.txt` row, a workflow job's `name:`). Renaming one is ALWAYS two commits: add the new job + `gates.txt` entry + re-run `ruleset-apply.sh --apply` to regenerate the live required-check set (commit + apply), confirm the new name green, THEN retire the old job + `gates.txt` entry + re-apply again — never a single commit that swaps a name outright, which would leave a push window where the ruleset requires a check no job produces (an unconditionally red `main`).

**No-path-filter rule**, reaffirmed: every job in `merge-gate.yml` triggers on every push to every non-`evidence` branch, unconditionally — a path-filtered required check never reports on an unaffected push and blocks that push forever (a known GitHub footgun this repo deliberately avoids). Docs-only and `rfc-*`-branch-only commits still run the full sixteen-job battery; per-branch `concurrency: cancel-in-progress` absorbs the repeated cost.

**Go-public close-out (RFC-005 slice 5).** `CONTRIBUTING.md` (repo root) is the contributor-facing doc: the validation bar (pointing back at this file's own "The validation bar" section and `docs/`), how to run the gates locally, the branch model stated for contributors (fast-forward-only `main` is the maintainer's own flow, not something a contributor reproduces), the honest current state of fork-PR CI (approval policy is live and repo-wide, but the `pull_request`-triggered workflow itself is slice 6 — not built yet), and crypto-contribution expectations (tests+vectors, CT discipline, the full affected-gate battery for secret-path changes). README gained a minimal `## Validation` section (prose pointing at `docs/ct-results.md`/`docs/mutation-results.md`/the RFC docs, plus the `merge-gate` badge pinned `?branch=main`) — **deliberately no job-name claims or claim table**; those co-land with their own drift check in slice 31, per the RFC's "no unchecked claims published in the gap" rule. `SECURITY.md` gained a "Trust root / security posture" section: everything upstream of the ruleset resolves to the owner account (`coreyleavitt`, a personal User, not an org — no self-hosted runners registered, verified live), split into independently-API-verified items (visibility, fork-PR approval policy, runner count) and owner-attested items (hardware-key 2FA, ghcr PAT scope/custody) that cannot be checked from an API session and are recorded as attested, not fabricated — see the handoff's open-fork entry asking Corey to confirm them.

## Conventions
- Port from permissively-licensed references (ref10/djb, TweetNaCl, orlp) and **attribute in the module header** as existing files do. Get functional correctness against vectors first, then CT-harden the signer.
- **Effects are declared, not inferred** (janus consumer finding 3): every `src/sello/` module carries `{.push raises: [], gcsafe.}` (the five `std/sysrand` fresh-secret constructors override with explicit `{.raises: [OSError].}`; `signing.nim`'s push and `keypair()` region widen by `SodiumInitError` under `-d:selloLibsodium`, matching `backend_sodium.nim`'s own push). New procs land under the nearest push automatically — if one genuinely must raise, give it an explicit per-proc annotation (or its own push/pop region, the `keypair()` precedent) rather than widening a module-level push. Pinned by `test_facade.nim`'s "declared effect contract" suite, which fails to compile if a declared effect grows.
- Secrets (signing, X25519 scalars): fixed-size stack `array[N, uintXX]`, never `seq`/`string`; zero allocation in the hot path.
- Scratch/diagnostic files from debugging sessions do not get committed — the maintained suite lives in `tests/unit/`, and `build/` catches binaries.
