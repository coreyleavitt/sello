# scripts/lib/gates.txt -- RFC-005 slice 3: the gates manifest, the single
# source of truth binding CI check names to the local command each gate
# runs. Three consumers read this file, per RFC-005 Part B's "the gates
# manifest is a data file" paragraph:
#   (i)   scripts/merge-gate.sh -- runs the required set locally (full,
#         or a named subset), reading BOTH columns.
#   (ii)  scripts/gates-manifest-check.sh (the "gates-manifest-sync" CI
#         job) -- asserts this file's check-name column (i) equals
#         .github/workflows/merge-gate.yml's job name set, in both
#         directions.
#   (iii) scripts/ruleset-apply.sh (RFC-005 slice 4) -- generates the
#         "main" ruleset's required-check array from column (i) alone,
#         never hand-written; scripts/ruleset-sync-check.sh (the
#         "ruleset-sync" CI check, also added in slice 4) generates the
#         same array the same way on the read/comparison side.
#
# This file is DATA, not executable (no shebang, no +x bit -- same
# convention as scripts/lib/milpa-pin.txt).
#
# Format: two whitespace-separated columns per line.
#   column 1 (check-name):        the CI check-run name -- MUST equal
#                                  the corresponding merge-gate.yml job's
#                                  `name:` field exactly (checked by
#                                  gates-manifest-check.sh), and becomes a
#                                  ruleset required-check key + a README
#                                  evidence-table row once those exist.
#   column 2 (script-invocation): the exact command scripts/merge-gate.sh
#                                  runs locally for that gate, handed to
#                                  `bash -c`.
# Comments start with `#` as the first non-whitespace character of the
# line (whole-line only -- no inline trailing comments, so the parser
# stays a single pass with no quoting rules to get wrong). Blank lines
# are ignored. Column 2 runs to the end of the line (so a future entry
# may carry arguments, e.g. `scripts/mutation.sh --full`); today every
# entry is a single bare script path.
#
# Script-invocation column, decided (RFC-005 slice 3): every entry here
# is the PLAIN script invocation -- NOT the `SELLO_IN_CONTAINER=1`-
# prefixed form merge-gate.yml's own `run:` steps use, and NOT prefixed
# with scripts/ci-setup.sh either. This works because every script named
# below is dual-mode (RFC-005 slices 1-3's standing convention): run with
# no SELLO_IN_CONTAINER set, each one wraps ITSELF in the pinned podman
# image automatically (host preflight + `podman run` against
# ghcr.io/coreyleavitt/nim:2.2.10) exactly like a maintainer's existing
# `scripts/test.sh` invocation always has; run with SELLO_IN_CONTAINER=1,
# each one assumes it is already inside that image (CI's own `container:`
# field) and skips the wrap. scripts/test.sh and scripts/check-readme.sh
# had this split as of RFC-005 slices 1-2; scripts/ci-property.sh gained
# it in THIS slice specifically so it could appear in this manifest as a
# literal, host-runnable command too (see its own header comment for the
# retrofit). scripts/ci-setup.sh (writes a bare zero-dep nim.cfg) is
# intentionally NOT part of any entry below: it exists for a bare CI
# checkout that has never run milpa at all, and every entry's own
# dual-mode host branch already assumes the documented prerequisite
# (`milpa fetch` run at least once -- see scripts/test.sh's own header)
# instead -- ci-setup.sh would be a harmless no-op locally (it only writes
# nim.cfg if absent) but is deliberately left off the column so this file
# states what actually runs, not an over-inclusive superset.
#
# RFC-005 slice 8 (clang-backend job): the first entries below to actually
# use column 2's documented "column 2 runs to the end of the line ... a
# future entry may carry arguments" allowance (see the paragraph above
# this one) -- `scripts/test.sh --cc clang` / `scripts/ci-property.sh
# --cc clang` thread Nim's `--cc:clang` into every compile in that run
# instead of the gcc default, via the SAME script both the gcc and clang
# checks share (no forked clang-flavored script -- RFC-005 Part B's
# build-path invariant). Both scripts' own header comments have the full
# --cc mechanics and the accompanying platform-identity canary
# (scripts/lib/toolchain-canary.sh) that proves, via Nim's own `--listCmd`
# output, which compiler actually got invoked -- not just which flag was
# passed.
#
# gates-manifest-sync (this file's own drift check) needs neither a
# container nor milpa -- it is a pure text scan over this file and the
# workflow YAML, so its script-invocation column entry runs unwrapped on
# a plain runner in CI and equally plain on a maintainer's host (see
# scripts/gates-manifest-check.sh's own header for the container-vs-
# plain-runner rationale).
#
# RFC-005 slice 9 (ASan/UBSan job): unit suite only, per Part B's merge-
# gate paragraph ("ASan/UBSan build of the unit suite") -- there is no
# property-linux-amd64-*-asan-ubsan sibling the way slice 8 added one for
# --cc, since the property suites are proptest's own generative harness,
# not sello's unit KATs, and the RFC scopes this leg to the unit suite
# deliberately. Runs on gcc (scripts/test.sh's own --sanitize header
# comment has the gcc-over-clang rationale), via the SAME
# scripts/test.sh both the gcc/clang legs and this one share (no forked
# sanitizer-flavored script -- RFC-005 Part B's build-path invariant).
#
# RFC-005 slice 11 (linux/arm64 legs): the first entries in this manifest
# whose script-invocation column hardcodes `SELLO_IN_CONTAINER=1` rather
# than relying on each script's own dual-mode host branch to auto-wrap in
# podman -- these two legs have NO container story at all (slice 7's
# manifest query found no arm64 variant of the pinned image; the
# recorded decision is a direct, checksum-pinned toolchain install
# instead, scripts/ci-nim-setup.sh's own header has the full writeup), so
# "in-container mode" (skip the podman wrapper, run the same commands
# directly) is the ONLY mode this leg ever runs in, locally or in CI --
# there is nothing to dual-mode against. scripts/ci-nim-setup.sh
# --expect-arch aarch64 is this leg's platform-identity canary (asserts
# `uname -m` before installing anything) AND the mechanism that puts a
# pinned `nim` on PATH (scripts/test.sh's own header documents the
# $HOME/.sello-nim/current on-disk convention it then picks up
# automatically) -- scripts/test.sh's existing toolchain-canary.sh call
# still runs unconditionally underneath, so this leg additionally proves
# gcc was really invoked, for free, exactly like every other leg.
#
# RFC-005 slice 12 (macOS-arm64 leg): unit suite only, no property
# sibling (see merge-gate.yml's own job comment for the full rationale --
# this runner has no milpa/proptest fetch story). Same
# SELLO_IN_CONTAINER=1-hardcoded register as the linux/arm64 legs above
# (no container to dual-mode against on macOS either) plus two additions
# specific to this leg: `--expect-arch arm64` (NOT `aarch64` -- Darwin's
# `uname -m` spelling differs from Linux's for the identical physical
# architecture) and scripts/test.sh's own `--expect-proptest-skip` flag
# (the inverse of every property-* row's implicit "banner absent"
# expectation: this leg has no proptest fetch story, so the banner's
# PRESENCE is the correct, asserted outcome).
#
# RFC-005 slice 13 (Windows/MinGW-gcc leg): the last hosted-native matrix
# leg. Same SELLO_IN_CONTAINER=1-hardcoded register as the arm64/macOS
# legs above (no podman/container story on Windows either) plus a second,
# NEW identity canary specific to this leg: `--expect-os
# 'MINGW64_NT*|MSYS*'`, asserted against the RAW `uname -s` value
# alongside the existing `--expect-arch x86_64`. Arch alone stops being
# sufficient here -- Git Bash's `uname -m` on 64-bit Windows reports
# `x86_64`, the SAME string a plain Linux amd64 host reports for the
# identical `uname -m` value, unlike the aarch64-vs-arm64 Linux/Darwin
# split every earlier leg could rely on -- so this leg's own
# scripts/ci-nim-setup.sh invocation would otherwise "pass" its arch
# canary on an ordinary Linux workstation running this manifest entry
# locally. `--expect-os` closes that gap directly (that script's own
# header has the full mechanism). `--with-mingw` additionally installs
# the pinned MinGW-w64 toolchain (scripts/lib/mingw-pin.txt) neither Nim's
# own Windows zip nor Windows itself ships, and asserts the installed
# `gcc --version` output matches the pin's own recorded version -- this
# leg's toolchain-identity canary, the direct analog of every other leg's
# scripts/lib/toolchain-canary.sh call (which still runs unconditionally
# underneath, via scripts/test.sh's own default `--cc` of gcc). Like every
# other hosted-only-residual gate above, running this entry on a
# non-Windows host fails loud at the OS canary, by design.
#
# RFC-005 slice 16 (build-smoke check, taken out of order -- slices
# 10/14/15 remain blocked on a Corey-owned ghcr write:packages credential
# for the sello-dev image; this slice needed only the always-available
# base ghcr.io/coreyleavitt/nim image, so it was pulled forward): compiles
# the fuzz external target (real SanitizerCoverage instrumentation) plus
# its driver and runs one deterministic input through the built target
# directly, and compiles (never runs) tests/ct/ct_main.nim -- the
# harnesses under tests/fuzz/ and tests/ct/ that would otherwise first
# compile at a maintainer's manual scripts/fuzz.sh/scripts/ct.sh
# invocation or a future nightly, discovered broken only then. Scope
# today is exactly these two harnesses; the taint (slice 19) and disasm
# (slice 23) binaries do not exist in this repository yet and are
# deliberately NOT covered -- those slices extend this same script/job in
# place. scripts/build-smoke.sh's own header comment has the full design,
# including why it reuses scripts/fuzz.sh --build-only /
# scripts/ct.sh --build-only rather than duplicating either script's
# build recipe, and the explicit no-verdict-authority statement for
# ct_main (RFC-005 Part B: hosted CI runs the dudect harness in
# compile-smoke mode only).
#
# RFC-005 slice 18 (API-surface gate, A8): two entries, one per build
# config the facade legitimately differs under (plain vs
# -d:selloLibsodium -- SodiumInitError, widened raises effects on the
# sign/keygen path). Both run scripts/api-surface-check.sh, which
# regenerates tests/api/api_surface_gen.py's facade-surface dump for its
# own config and diffs it against the committed baseline at
# tests/api-surface/expected/<config>.txt via the shared
# scripts/lib/baseline.sh idiom -- that generator's own module doc
# comment has the full spike writeup (mechanism chosen, recorded blind
# spots) and scripts/api-surface-check.sh's own header has the gate
# -level rationale. Both entries needed only the always-available base
# ghcr.io/coreyleavitt/nim image (verified empirically during this
# slice's own spike that the facade-surface generator never invokes a C
# compiler/linker -- `nim jsondoc` is a Nim-semantic-pass-only tool, so it
# resolves selloLibsodium's FFI `{.importc, header.}` declarations without
# ever needing libsodium-devel installed) -- landed as a full dual-config
# gate this slice, not deferred to the sello-dev credential fork the way
# slices 10/14/15/17 are.
#
# RFC-005 slice 10 (--cpu:i386 32-bit leg): unit suite only, per the same
# "matches the sanitizer leg's own scoping" register `--sanitize
# asan-ubsan` above already established -- verified in-slice, not merely
# assumed by analogy: the full property suite DOES compile and pass under
# a real (non-emulated) --cpu:i386 build inside sello-dev, but its
# generative-example wall clock runs several times slower than the same
# suite's amd64 native run (int64 arithmetic becoming register-pair
# operations under -m32 is directly on the hot path of every property
# file's generated examples, not just this leg's identity canary), enough
# to threaten the merge-gate wall-clock budget property-linux-amd64-gcc
# already sits close to -- so, per this slice's own "confident call either
# way, recorded" instruction, this leg stays unit-only, with no
# property-linux-i386-gcc sibling. `scripts/test.sh --cpu i386`'s own
# header comment has the full `--cpu:i386` + `--passC:-m32 --passL:-m32`
# mechanism (an empirically REPRODUCED finding, not assumed: `--cpu:i386`
# alone is not enough -- gcc happily emits a 64-bit object under a Nim
# frontend that believes it targeted i386 unless `-m32` is threaded
# explicitly, caught downstream only by nimbase.h's own
# `NIM_STATIC_ASSERT` on pointer/NI size agreement) and
# scripts/lib/cpu-canary.sh's own header has the platform-identity canary
# design ("Identity canary: pointers are 4 bytes" -- RFC-005 Part B's own
# text for this leg, verified via a REAL `doAssert` at runtime, not
# merely inferred from --listCmd text the way every other canary in this
# file does it). This is the first entry in this manifest whose plain,
# unwrapped script-invocation column resolves a DIFFERENT container image
# than the base `ghcr.io/coreyleavitt/nim` one on a maintainer's host --
# `scripts/test.sh`'s own `--cpu` handling sources
# scripts/lib/sello-dev-image.sh and pulls `sello-dev` by digest instead,
# since only that image carries the `gcc-32bit`/`glibc-devel-32bit`/
# `libstdc++6-32bit` packages this leg needs (Containerfile, RFC-005
# slice 7) -- the manifest's own "plain, host-runnable command" convention
# still holds with no new logic needed in merge-gate.sh itself.
#
# RFC-005 slice 31 (README evidence table + drift check): a pure text
# scan over README.md's validation-map table plus its badge/platform/
# CT-scope sections (round-2 corrections (i)-(iii) to the Part B
# evidence-story paragraph) -- no Nim/podman/milpa needed, same
# no-container register as gates-manifest-sync/ruleset-sync/policy-lint
# above. scripts/validation-map-check.sh's own header has the full
# mechanism (parsing, per-category assertions, the CT-scope-vs-
# image-pins.txt version cross-check).
#
# RFC-005 slice 14 (libsodium differential job): the second entry, after
# unit-linux-i386-gcc, whose plain, unwrapped script-invocation column
# resolves the `sello-dev` image rather than the base
# `ghcr.io/coreyleavitt/nim` one -- scripts/test-libsodium.sh has always
# pulled sello-dev by digest (RFC-005 slice 7), so unlike --cpu:i386 this
# needed no new image-resolution logic, only the same
# SELLO_IN_CONTAINER=1 dual-mode retrofit scripts/test.sh/
# scripts/ci-property.sh already had. Named `unit-linux-amd64-gcc-libsodium`
# rather than a `libsodium-*`-prefixed name -- matches the existing
# job-naming axis exactly (`unit-<os>-<arch>-<compiler>[-variant]`, the
# same axis `unit-linux-amd64-gcc-asan-ubsan` already established for a
# build-config variant of the plain gcc leg), rather than inventing a
# second axis for one job. Unit suite only, no property sibling -- this
# job fetches no proptest of its own (scripts/test-libsodium.sh never
# has), so the property files self-skip exactly as they did before this
# slice, unaffected by SELLO_REQUIRE_LIBSODIUM=1 (a differently-worded,
# unbracketed banner -- see that script's own header comment for why the
# two skip registers cannot collide). scripts/test-libsodium.sh's own
# header comment has the full SELLO_REQUIRE_LIBSODIUM=1 design (the
# test-file-level doAssert plus this script's own belt-and-suspenders
# `[SKIPPED]`-marker grep) -- the mechanism that makes this job's own
# silent-skip-must-be-red DoD hold.
#
# RFC-005 slice 15 (mutation + bmc jobs, taken in numeric order once the
# ghcr write:packages credential unblocked slice 14): `mutation` needs
# only the base ghcr.io/coreyleavitt/nim image (scripts/mutation.sh's own
# header comment has the "why not sello-dev" rationale); `bmc-symex` needs
# sello-dev (z3-devel). Both entries are the plain, unwrapped
# scripts/<name>.sh invocation, per this file's own standing convention --
# each script's own SELLO_IN_CONTAINER dual-mode split (RFC-005 slice 15's
# retrofit to both scripts) makes that work locally exactly the way every
# other entry in this manifest already does. `bmc-symex`'s script-
# invocation column carries an explicit timeout argument
# (`scripts/bmc.sh 600`), matching the merge-gate workflow's own job step
# exactly -- see CLAUDE.md's own "Mutation + bmc jobs" CI paragraph for
# the calibrated value and the timeout-triage policy.
